# 한글 캡션(그림·표) 읽기·고치기

AI 가 한글(HWP·HWPX) 문서의 **그림 캡션과 표 캡션** 글도 읽고 고칩니다. 이 문서는 어떻게 하는지, 코어(rhwp 0.8.6)에서 확인한 것, 확인한 방법과 수치, 한계를 적습니다.
코어를 직접 불러 실험해서 확인한 것과 소스(`edwardkim/rhwp` v0.8.6)를 읽고 안 것을 구분해 적었습니다.

## 하는 일

- 글 캡션이 달린 그림(본문 문단·표 칸·글상자 안 어느 깊이든)과 **본문 문단에 바로 놓인 표**의 캡션 글을 읽고, 글 바꾸기·글자 서식·문단 서식(본문에 놓인 개체의 캡션만)·되돌리기를 합니다.
- 캡션 문단은 개체가 든 문단 다음에 옵니다. 표 캡션은 표의 캡션 방향(위·왼쪽이면 표 칸 문단들 앞, 아래·오른쪽이면 뒤)을 따릅니다.
- 카드의 위치 문구는 **"그림 캡션 1"**(캡션이 달린 그림을 문서 순서로 센 번호)과 **"표 2 캡션"**(표 칸의 "표 2 · 3행 1열"과 같은 표 번호)입니다. `AreaPlace`(`shared/src/style.ts`)에 `kind: 'caption'`, `of: 'picture' | 'table'`, `number` 로 담깁니다.
- 서식 점검(문서 안 일관성·기준 문서)은 본문(표 밖)만 비교하므로 캡션은 넣지 않습니다. 서식 규칙은 **"캡션"**을 적었을 때만 캡션에 적용합니다(AI 프롬프트·데모 AI 가 같은 원칙). 맞춤법·말투 교정은 캡션에도 적용합니다.
- 읽지 못하는 캡션: 표 칸·글상자 안에 놓인 표의 캡션, 도형(사각형 등)·묶음 개체의 캡션. 코어에 그곳을 가리키는 길이 없습니다(아래 표).

## 코어가 캡션에 닿는 길 — 소스에서 확인하고 코어를 불러 실험으로 확인

| 대상 | 경로 함수(`*InCellByPath`) | 평평한 함수(`*InCell`, 본문 문단의 컨트롤만) |
| --- | --- | --- |
| 그림 캡션 | 됨. 경로 한 단계 = `{controlIndex: 그림, cellIndex: 0, cellParaIndex}`, 어느 깊이든 | 됨. `(구역, 본문 문단, 그림 컨트롤, 칸 번호 0, 캡션 문단)` |
| 표 캡션 | **안 됨**(칸 번호 65534 를 칸으로 읽어 "셀 65534 범위 초과"를 냄. 만든 문서로 확인) | 됨. **칸 번호에 65534**(`TABLE_CAPTION_CELL_SENTINEL`)를 넣는다. 표가 본문 문단에 바로 놓였을 때만 |
| 사각형 등 도형·묶음 개체의 캡션 | 안 됨(글상자 글만) | 안 됨(글상자 글만) |

- 근거: `src/document_core/queries/cursor_nav.rs`(`resolve_paragraph_by_path`), `src/document_core/commands/text_editing.rs`(`get_cell_paragraph_ref/mut`, `get_cell_paragraph_count_native`).
- 글 읽기·삽입·삭제와 글자 서식(읽기·쓰기)·문단 서식(읽기·쓰기)을 모두 만든 문서로 확인했습니다(`web/src/engines/hwp/caption.test.ts`).
  경로 함수는 글·글자 서식만 되고 문단 서식 함수가 없습니다(글상자와 같은 한계). 그래서 문단 서식(정렬·줄 간격)은 본문 문단에 바로 놓인 그림과 표의 캡션만 바꾸고, 표 칸·글상자 안에 놓인 그림의 캡션은 이유와 함께 거절합니다.
- 캡션 만들기(시험 문서용): `setPictureProperties(구역, 문단, 컨트롤, '{"hasCaption":true}')`, `setTableProperties(…, '{"hasCaption":true,"captionDirection":2}')`.
  표 속성의 `captionDirection` 은 숫자(0 왼쪽, 1 오른쪽, 2 위, 3 아래. 소스의 열거형 순서이고, 2 로 정하면 캡션이 표 칸보다 앞에 오는 것을 시험으로 확인했습니다). 그림 속성의 `captionDirection` 은 문자열이며 우리는 쓰지 않습니다(그림 캡션은 항상 개체가 든 문단 다음에 둡니다).
- 코어는 메모리에서 만든 문서의 표 캡션을 내보냈다가 다시 열면 글 끝에 공백을 하나 붙입니다(왕복해도 더 늘지는 않고, 예제 문서의 캡션은 왕복해도 같았습니다). 그림 캡션에서는 없었고, 원인은 코어의 동작이라 따로 보정하지 않았습니다.

## 걸림돌: 캡션 안의 자동 번호("번호 넣기")

"그림 1 시스템 구성도"의 **1** 은 글이 아니라 자동 번호 컨트롤입니다.

- 코어는 그 자리를 글 속에 **공백 한 글자(U+0020)**로 보여 줍니다. 내보낸 HWPX 의 XML 과 대조해 확인했습니다. 코어가 새 캡션에 넣는 글은 `"그림  "`(라벨 + 번호 자리 + 공백)이고
  XML 에서는 `<hp:t>그림</hp:t><hp:autoNum/><hp:t> </hp:t>`, 실제 문서처럼 라벨 뒤에 공백을 하나 더 넣으면 `그림 ` + 번호 + ` 시스템 구성도` 입니다. 코어가 돌려주는 글은 `"그림   시스템 구성도"`(공백 셋)입니다.
- AI 에게 그대로 보이면 **"공백이 셋"을 고치자고 제안할 수 있습니다.** 코어의 글 삽입·삭제는 번호 컨트롤을 지우지 않지만, 번호 자리 글자를 지워도 코어는 글자 수에 반영하지 않고(번호는 남음, 되돌리면 진짜 공백으로 바뀔 수 있음), 번호 둘레의 공백을 바꾸면 번호의 자리가 어긋날 수 있습니다.
- 캡션 안 컨트롤의 위치를 알려 주는 함수는 없습니다. `getControls()` 는 그림·표 캡션 안 컨트롤을 목록에 넣지 않고, `getControlTextPositions` 는 본문 문단 전용이고, 경로 방식 선택 내보내기에는 번호가 글로 나오지 않습니다.
- **코어 자신도 번호 자리를 글의 모양으로 어림합니다.** 그리기 코드(`renderer/layout/paragraph_layout.rs` 의 `apply_auto_numbers_to_composed`)가 글의 첫 "공백 둘"(`"  "`) 뒤에 번호 글자를 끼워 넣어 그립니다(HWP5·HWPX·HWP3 공통).

### 우리의 방법

1. **어림**(`captionNumberZone`, `web/src/engines/hwp/model.ts`): 글이 공백으로 시작하지 않고 첫 공백 덩어리가 둘 이상이며 그 덩어리의 둘째 글자가 일반 공백(U+0020)이면, 그 둘째 글자가 번호 자리입니다.
   글에서 그 자리를 **№** 표지로 바꿔 AI 에게 보여 줍니다(글자 수가 같아 글자 위치는 그대로입니다). AI 프롬프트가 "№는 자동 번호가 든 자리이니 find·replace 에 넣지 말고 그 둘레 공백도 건드리지 마라"고 알립니다.
2. **보호**: 바꾸는 범위가 첫 공백 덩어리와 겹치거나, 덩어리 가장자리에 공백을 붙이는 변경(`touchesCaptionNumber`)은 "캡션의 번호가 든 자리와 그 둘레 공백은 바꿀 수 없어요"라는 이유로 거절합니다(한 묶음이면 묶음 전체가 취소됩니다). 라벨이나 번호 뒤의 글을 바꾸는 것, 글 끝에 덧붙이는 것은 됩니다.
3. 글자 서식은 문단 전체에 적용되므로 번호 글자에도 같은 서식이 입혀집니다(번호가 캡션 글과 같은 모양이 됩니다).

### 어림이 맞는지 — 예제 전체(900개)로 확인

- 예제 중 캡션이 달린 그림·표가 든 69개 문서를 코어로 내보낸 HWPX XML 과 대조했습니다. **번호 컨트롤이 든 캡션 492개 모두**에서 어림이 번호 자리를 맞혔고, 그 자리의 글자는 모두 일반 공백(U+0020)이었습니다.
- 번호 없는 캡션이 번호 자리로 보이는 경우(사람이 공백을 연달아 쓴 곳)는 있습니다. 그 자리를 건드리는 변경이 거절될 뿐 문서가 깨지지는 않습니다. 사람이 친 숫자 폭 공백(U+2007: `Fig. ` + U+2007 + `1.` 꼴, `basic__treatise sample.hwp`)은 번호 자리가 아니므로 일반 공백일 때만 번호 자리로 봅니다(예제 전체 대조에서 이 문서가 걸려 고쳤습니다).
- 코어가 새 캡션에 넣는 `"그림  "` 꼴은 번호 자리가 덩어리의 첫 글자라 표지가 한 글자 뒤에 붙습니다. 덩어리 전체를 건드리지 않으므로 번호는 지켜집니다.

### 문서에서 보기: 편집기의 글자 위치가 번호 뒤에서 어긋난다

코어는 그리기 전에 캡션 글에 번호 글자를 끼워 넣습니다(위). 그래서 캐럿·선택 위치를 구하는 코어 함수(`getCursorRectInCell`, `getSelectionRectsInCell` 등)와 그것을 쓰는 편집기의 글자 위치는
글을 읽고 고치는 함수의 글자 위치와 달리 **번호 뒤에서 번호의 글자 수(1 이상)만큼 어긋납니다.** Node 에서 코어를 직접 불러도, 실제 편집기에서도 같았습니다:
표 캡션 `표 1 월별 실적 되요 라고 적습니다`(코어가 주는 글 기준으로 `되요`는 10번째 글자부터)에서 `되요`를 선택하려고 위치 10~12 를 넘기면 `(공백)되`가 선택되고(위치 11~13 이 `되요`), 그림 캡션도 같습니다(편집기를 확대한 화면으로 확인).
캐럿 위치 계산은 글 길이 + 번호 글자 수까지가 유효하고 그 뒤로는 처음 위치로 돌아갑니다(번호 한 자리와 두 자리 표로 확인).
번호 글자 수는 번호 형식(한 자리, 두 자리, 앞뒤 장식 문자)에 따라 다르고 알려 주는 함수가 없어서, **번호 뒤의 글은 선택하지 않고 번호 앞에 캐럿만 두고 알립니다**("캡션의 번호(자동 번호) 때문에 … 번호 앞에 커서를 두었어요"). 엉뚱한 글이 선택돼 보이는 것보다 낫다고 판단했습니다.
번호 앞의 글(라벨)과 번호 없는 캡션의 글은 정확히 선택합니다. 이 알림이 뜨는 동작은 `e2e/hwp-caption.spec.ts` 가 확인합니다(선택 표시가 없는 것까지).

읽은 캡션의 개수와 글은 900개 모두 코어를 직접 걸으며 읽은 것과 같았습니다(위).

## 한계

- **표 칸·글상자 안에 놓인 표의 캡션과 도형·묶음 개체의 캡션은 읽지 못합니다.** 코어에 닿는 길이 없습니다(표 안의 표 캡션은 만든 문서로, 경로 함수가 칸 번호 65534 를 거절하는 것까지 확인했고, 도형·묶음 개체는 함수 목록·소스로 확인했습니다). 읽지 못하는 글은 AI 에게 넘기지 않고 고치지도 않습니다.
  예제 900개에서 읽지 못하는 캡션은 33개입니다(아래 "읽지 못하는 캡션의 수").
- 번호 자리는 글의 모양으로 어림한 것이라 틀릴 수 있습니다(번호가 든 자리를 못 찾으면 그 둘레 공백을 바꾸는 변경이 거절되지 않습니다. 실제 예제 492개는 모두 맞혔지만 모든 문서를 대표하지는 않습니다).
- 번호 뒤의 글은 문서에서 보기가 글을 선택하지 못하고 번호 앞에 캐럿만 둡니다(위).
- 문단 서식(정렬·줄 간격)은 본문 문단에 바로 놓인 그림·표의 캡션만 바꿉니다.
- 고쳐 내보낸 파일의 캡션이 한컴오피스에서 같게 열리는지는 확인하지 못했습니다(다시 읽는 쪽도 같은 rhwp 입니다).

## 이어서 할 수 있는 것

- 번호 글자 수를 알아내 번호 뒤의 글도 정확히 선택하기. 캐럿 위치 계산(`getCursorRectInCell`)이 유효한 마지막 위치를 조사하면 번호 글자 수를 알 수 있습니다(글 길이 + 번호 글자 수까지가 유효하고 그 뒤는 처음 위치로 돌아감). 다만 코어의 동작에 기대는 방법이고 줄이 바뀌는 캡션까지 따져야 해서 하지 않았습니다.
- 표 안의 표 캡션은 코어에 길이 생기면 읽을 수 있습니다(경로 함수가 칸 번호 65534 를 받아들이면 `buildBodySlots` 의 `tableCaption` 을 경로로 넓히면 됩니다).

## 로컬에서 이어서 하는 법

```bash
git clone https://github.com/ZN9812/AllDoc.git && cd AllDoc
git checkout claude/web-document-editor-design-4kd6km
npm ci
npm run build                      # 한글 편집기(rhwp-studio)와 예제 문서를 .cache 에 받는다
npm run typecheck && npm test
REQUIRE_HWP_SAMPLES=1 npm test -w web -- src/engines/hwp/corpus.test.ts   # 예제 12개 대조
npx playwright test e2e/hwp-caption.spec.ts --project=desktop              # 종단 시험(빌드 뒤)
```

  후 `git checkout v0.8.6`, `samples/` 와 `src/` 를 본다. 이 저장소의 `.cache` 는 예제 12개만 sparse 로 받는다. 받은 `samples/` 를 한 폴더에 모아 `RHWP_SAMPLES_DIR` 로 가리키면 `corpus.test.ts` 가 그 전체로 돈다.

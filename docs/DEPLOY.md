# 배포 방법

서버 한 대에서 Docker로 띄우는 방법을 먼저 설명하고, Docker 없이 띄우는 방법과 공개 전 점검표를 이어서 적었습니다.

> **공개 운영 전에 꼭 읽으세요: [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md)의 "SuperDoc의 독점 DOCX 엔진".**
> Word(DOCX) 편집에 쓰는 부품 하나가 오픈소스가 아닌 독점 라이선스입니다. 운영 형태에 맞는지 SuperDoc과 변호사에게 확인하거나, 아래 "Word 지원 없이 배포하기"로 끄고 배포하세요.

## 준비물

- 서버(리눅스 권장)와 Docker. 문서 처리는 사용자의 브라우저가 하고, 서버는 로그인·횟수 관리·AI 중계·정적 파일만 합니다. 시험 중 서버 컨테이너는 종단 시험 전체를 돌린 뒤에도 메모리를 약 85MB 썼습니다(실제 사용자 수에 따른 부하는 확인하지 않았습니다).
- 도메인과 HTTPS. 구글 로그인이 HTTPS 주소를 요구하고, 쿠키도 HTTPS에서만 안전하게 쓰입니다.
- 구글 로그인 클라이언트(아래 "구글 로그인 설정"), AI를 쓸 거라면 Anthropic API 키.

## 설정 값

`.env.example`을 `.env`로 복사해 채웁니다. `.env`는 저장소에 올리지 마세요(이미 `.gitignore`에 있습니다).

| 이름 | 필수 | 설명 |
| --- | --- | --- |
| `PUBLIC_URL` | 예 | 사용자가 접속하는 주소(예: `https://docs.example.com`). 구글 로그인 되돌아오기 주소와 쿠키 설정에 쓰입니다. `https://`로 시작하면 보안 쿠키·HSTS가 켜집니다. |
| `SESSION_SECRET` | 예 | 로그인 세션 서명용 비밀 문자열, 32자 이상. `openssl rand -hex 32` |
| `AUTH_MODE` | 예 | `google`(운영) · `none`(로그인 없이 AI 사용, 한도 없음, 사내망용) · `dev`(개발용 가짜 로그인, 운영에서는 시작되지 않습니다) |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | `google`일 때 | 구글 OAuth 클라이언트 |
| `AI_PROVIDER` | 아니오 | `anthropic`(기본) · `mock`(데모) · `off`. 자세한 내용은 [AI.md](AI.md) |
| `ANTHROPIC_API_KEY` | `anthropic`일 때 | 서버에만 둡니다. |
| `AI_CONFIG_PATH` | 아니오 | 작업별 모델·시스템 프롬프트 설정 파일(JSON). [AI.md](AI.md) |
| `DAILY_AI_LIMIT` | 아니오 | 사용자별 하루 AI 요청 수(기본 5). `PLANS_CONFIG_PATH` 가 없을 때 기본 요금제(free)의 하루 한도가 됩니다. |
| `PLANS_CONFIG_PATH` | 아니오 | 요금제 파일(JSON). 아래 "요금제와 관리자 도구" |
| `AI_DAILY_BUDGET_USD` | 아니오 | 전체 사용자의 하루 AI 원가 상한(달러). 원장 기준으로 넘으면 그날은 AI 요청을 모두 503 으로 멈춥니다. Anthropic 콘솔의 월 지출 한도와 함께 쓰세요. |
| `TERMS_VERSION`, `TERMS_URL`, `PRIVACY_URL` | 아니오 | 약관 판과 이용약관·개인정보처리방침 주소. 판을 넣으면 로그인한 사용자가 그 판에 동의(만 14세 이상 확인 포함)해야 AI 를 쓸 수 있고, 판을 바꾸면 다시 묻습니다. 판을 넣으면 두 주소도 있어야 합니다. |
| `BACKUP_DIR`, `BACKUP_KEEP` | 아니오 | 하루 한 번 데이터 파일 스냅숏을 둘 폴더(기본 `DATA_DIR/backups`)와 남길 개수(기본 14, `0` 이면 끔). 아래 "백업" |
| `APP_TIMEZONE` | 아니오 | 하루가 바뀌는 시간대(기본 `Asia/Seoul`) |
| `PORT` | 아니오 | 서버가 듣는 포트(기본 8787). Docker에서는 그대로 두고 바깥 포트만 바꾸는 편이 쉽습니다. |
| `DATA_DIR` | 아니오 | SQLite(계정, 사용 횟수, AI·컴파일 원장, 요금제 부여, 관리 기록)와 컴파일하려고 받은 파일(`tex/`)을 둘 폴더. 이미지 안에서는 `/data` |
| `COMPILER` | 아니오 | LaTeX 컴파일: `off`(기본, 컴파일 없음) · `mock`(데모 컴파일러, 실제 TeX 아님) · `http`(컴파일 일꾼). 아래 "LaTeX 컴파일" |
| `COMPILER_URLS`, `COMPILER_SECRET` | `http`일 때 | 일꾼 주소(쉼표로 여러 개, 차례로 돌려 씀)와 요청 서명 비밀값(32자 이상, 일꾼과 같은 값) |
| `COMPILER_CONCURRENCY`, `COMPILER_QUEUE` | 아니오 | 서버 전체 동시 컴파일 수(기본 2)와 기다릴 수 있는 수(기본 10, 넘으면 `503` + `Retry-After`) |
| `TEX_RETENTION_DAYS` | 아니오 | 컴파일하려고 받은 파일을 마지막으로 쓴 날부터 며칠 두는지(기본 7, **임시 값·결정 필요**) |
| `ALLOWED_ORIGINS` | 아니오 | `PUBLIC_URL` 외에 요청을 받아들일 출처(쉼표로 구분). 보통 필요 없습니다. |

설정이 잘못되면 서버가 켜질 때 무엇이 문제인지 한국어로 알려 주고 멈춥니다.

## 구글 로그인 설정

로그인은 AI 사용 횟수와 요금제를 사용자별로 관리하려는 용도로만 씁니다(문서는 로그인과 상관없이 브라우저에만 저장됩니다).

1. [Google Cloud Console](https://console.cloud.google.com/)에서 프로젝트를 만들고 "API 및 서비스 → OAuth 동의 화면"을 설정합니다.
2. "사용자 인증 정보 → OAuth 클라이언트 ID 만들기 → 웹 애플리케이션"을 고릅니다.
3. **승인된 리디렉션 URI**에 `{PUBLIC_URL}/api/auth/callback`을 넣습니다(예: `https://docs.example.com/api/auth/callback`).
4. 발급된 클라이언트 ID와 보안 비밀을 `.env`의 `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`에 넣습니다.

서버는 인증 코드 방식(PKCE 포함)으로 로그인합니다. 서버 저장소(SQLite)에는 다음이 남습니다.
- **계정**: 사용자 번호(구글 계정 식별값), 이름·이메일, 가입·마지막 로그인 시각, 상태(차단 여부), 약관 동의 판·시각
- 날짜별 AI 사용 횟수(62일 보관), AI 요청별 사용량(토큰·원가·모델, 문서 글은 없음. [AI.md](AI.md)), 관리자가 준 요금제, 관리 기록

세션 쿠키는 서명만 하고 서버에 목록을 두지 않지만, 요청마다 계정을 한 번 조회해 탈퇴·차단·"모든 기기에서 로그아웃"을 바로 반영합니다(쿠키 안의 세션 버전이 계정의 버전과 달라지면 무효).
**이 기능이 들어간 판으로 올리면 그 전에 받은 쿠키는 모두 무효가 되어 사용자가 한 번 다시 로그인해야 합니다.**

계정을 지우면(설정 → 계정 → 계정 삭제, 또는 관리자 도구) 이름·이메일을 지우고 모든 쿠키를 무효로 하며, 원장의 사용자 번호를 되돌릴 수 없는 가명으로 바꿉니다. 날짜별 사용 횟수는 같은 계정으로 다시 가입해 한도를 되돌리지 못하도록 남겨 두고 62일 뒤 지웁니다. 백업 스냅숏에는 보관 기간(기본 14일) 동안 남습니다.

## Docker로 실행

```bash
docker compose up -d --build        # .env 를 먼저 채우세요
docker compose logs -f alldoc       # "서버가 … 실행 중입니다" 가 보이면 됩니다
```

또는 compose 없이:

```bash
docker build -t alldoc .
docker run -d --name alldoc --restart unless-stopped -p 8787:8787 --env-file .env -v alldoc-data:/data alldoc
```

- 빌드할 때 **한글 편집기(rhwp-studio)를 GitHub에서 받아 빌드**합니다(정해 둔 버전·커밋과 다르면 중단). 그래서 빌드하는 곳은 인터넷(GitHub, npm)에 나갈 수 있어야 합니다.
  Docker 빌드는 한글 편집기를 준비하지 못하면 **실패**하도록 되어 있습니다(`RHWP_STUDIO_STRICT=1`). HWP 편집이 빠진 이미지가 조용히 만들어지지 않게 하려는 것입니다.
- 이미지는 컨테이너 안에서 일반 사용자(`node`)로 실행되고, 사용 횟수 데이터는 `/data`(볼륨)에 저장됩니다. 컨테이너를 지워도 볼륨은 남습니다.
- 건강 확인(`/api/health`)이 이미지에 들어 있어 `docker ps`에서 `healthy`로 보입니다.
- 이 저장소의 Dockerfile로 이미지를 처음부터 빌드(npm ci, 한글 편집기 받기·빌드, 웹·서버 빌드)해서 컨테이너로 띄우고, 같은 종단 시험(데스크톱·휴대폰)을 그 컨테이너에 돌려 통과한 것을 확인했습니다.
  이 확인은 인터넷에 나가려면 프록시가 필요한 시험 환경에서, 프록시 설정 몇 줄만 덧붙인 같은 Dockerfile로 했습니다. 덧붙인 줄을 뺀 Dockerfile 그대로는 빌드해 보지 못했습니다.
  운영 설정(구글 로그인, 진짜 AI)은 키가 있어야 해서 이 확인에 들어 있지 않습니다. `docker-compose.yml`은 `docker compose config`로 문법만 확인했습니다.

### 백업

데이터 파일에는 계정·요금제 부여·AI 사용량 원장(가격을 정하는 근거)이 들어 있어 잃으면 다시 만들 수 없습니다.
- 서버가 **하루 한 번** 스냅숏을 만듭니다: `BACKUP_DIR`(기본 `/data/backups`)의 `alldoc-YYYY-MM-DD.sqlite`, 최근 `BACKUP_KEEP`(기본 14)개. 서버를 켤 때와 그 뒤 한 시간마다 "오늘 것이 있는지" 보고 없으면 만듭니다(SQLite `VACUUM INTO`, 서버를 멈추지 않음).
- **스냅숏은 같은 디스크에 있으므로, 서버 밖으로 복사하는 일은 직접 하세요**(예: restic·rclone 으로 `/data/backups` 를 다른 곳에 매일 복사). 같은 볼륨만으로는 디스크 고장에 대비할 수 없습니다.
- **되살리기**: 서버를 멈추고 → 데이터 폴더의 `alldoc.sqlite`, `alldoc.sqlite-wal`, `alldoc.sqlite-shm` 을 다른 곳으로 옮긴 뒤 → 원하는 스냅숏을 `alldoc.sqlite` 이름으로 복사하고 → 서버를 켭니다. 스냅숏 이후의 기록(사용 횟수·원장)은 사라집니다.
- **복구 훈련 기록**(2026-10-14, 이 저장소의 빌드한 서버로 개발 환경에서 한 번 해 본 것이며 CI 에서는 돌지 않는다): 개발용 로그인으로 계정을 만들고 데모 AI 요청 1건과 관리자 요금제 부여 1건을 남김 → 서버를 다시 켜 스냅숏 생성 → 데이터 폴더를 옮겨 "잃은" 상태로 만듦 → 스냅숏을 복사해 서버를 켬(되살려 다시 띄우는 데 약 0.35초) → 옛 쿠키로 로그인 상태, 수동 부여 요금제, 오늘 사용 1회, 원장 1건, 관리 기록 1건이 모두 남아 있음을 확인. Docker 볼륨과 서버 밖 복사는 이 훈련에 들어 있지 않습니다.

**사용자의 문서는 서버에 없습니다.** 각자의 브라우저에 있으므로 서버 백업으로는 복구되지 않습니다(사용자가 "내려받기"로 보관해야 합니다).

### 요금제와 관리자 도구

결제는 아직 없습니다. 요금제는 파일로 정하고, 관리자가 사용자에게 수동으로 줍니다(베타 시험자 등).

```json
{
  "default": "free",
  "plans": [
    { "id": "free", "name": "무료", "limits": { "aiRequestsPerDay": 5, "aiRequestsPerMonth": 60, "aiMaxDocChars": 60000, "aiCostCapMicroUsdPerMonth": 3000000,
      "compileTimeoutSec": 60, "compilesPerDay": 50, "compileSecondsPerDay": null, "projectMaxBytes": 52428800 } },
    { "id": "pro", "name": "프로", "limits": { "aiRequestsPerDay": null, "aiRequestsPerMonth": 600, "aiMaxDocChars": 120000, "aiCostCapMicroUsdPerMonth": 30000000 } }
  ]
}
```
- `null` 은 제한 없음입니다. 컴파일 한도 4개(`compileTimeoutSec` 컴파일 한 번의 시간 제한(초), `compilesPerDay`, `compileSecondsPerDay`, `projectMaxBytes` 프로젝트 전체 크기)는 적지 않으면 임시 기본값(60초, 제한 없음, 제한 없음, 50MB)을 씁니다. **이 기본값은 정한 값이 아닙니다**(무료 사용자에게 컴파일을 줄지, 시간 제한을 얼마로 할지는 결정 필요, `docs/PRODUCT.md`). `aiMaxDocChars` 는 120,000 이하, `aiCostCapMicroUsdPerMonth` 는 한 사용자의 한 달 AI 원가 상한(마이크로달러, 3000000 = $3)이며 화면에 알리지 않는 안전 장치입니다. 위 숫자는 형식을 보이려는 예시이고 정한 가격·한도가 아닙니다.
- 파일이 잘못되면(기본 요금제가 없음, id 가 겹침, 모르는 항목) 서버가 켜질 때 알려 주고 멈춥니다. compose 에서는 `./plans.json:/config/plans.json:ro` 로 붙이고 `PLANS_CONFIG_PATH=/config/plans.json` 을 적습니다.
- 관리자 도구(같은 설정·데이터 폴더로 실행. 바꾸는 명령은 모두 관리 기록에 남습니다):

```bash
docker compose exec alldoc node --disable-warning=ExperimentalWarning server/dist/admin.js user someone@example.com
docker compose exec alldoc node --disable-warning=ExperimentalWarning server/dist/admin.js grant g:1234 pro --days 30 --note 베타
# 그 밖에: plans · revoke · ban · unban · logout-all · role · delete --yes · audit
```

## LaTeX 컴파일

LaTeX 프로젝트는 브라우저에 저장하고, PDF 를 만들 때만 서버로 보냅니다(설계: [LATEX.md](LATEX.md)).

- **구성**: 앱 서버는 로그인·약관·요금제 한도·파일 확인·대기열을 맡고, 실제 컴파일은 별도 이미지의 **컴파일 일꾼**(`compiler/`)이 내부망에서 합니다. 일꾼은 비밀값·DB·파일 저장소를 갖지 않고, 작업마다 받은 파일만 작업 폴더에 썼다가 지웁니다. docker 소켓은 어디에도 넘기지 않습니다.
- **띄우기**: `.env` 에 `COMPILER=http`, `COMPILER_URLS=http://compiler:8790`, `COMPILER_SECRET=<32자 이상>` 을 적고 `docker compose --profile latex up -d --build`. compose 의 `compiler` 서비스는 내부망(`internal: true`)만 쓰고, 읽기 전용 루트, `/work`·`/tmp` 용량 상한 tmpfs, `cap_drop: ALL`, `no-new-privileges`, 프로세스·메모리·CPU 상한, **`compiler/seccomp.json`**(Docker 기본 프로필 + `unshare setns mount umount2 pivot_root clone clone3`)으로 뜹니다.
- **작업마다**: bubblewrap 으로 이름공간(네트워크·PID 등)을 나누고 환경 변수를 비운 뒤 TeX Live·글꼴만 읽기 전용, 작업 폴더만 쓰기로 붙입니다. `prlimit` 으로 주소 공간(2GB)·CPU 시간·파일 크기(200MB)·프로세스 수를 막고, 시간 제한을 넘으면 프로세스 묶음을 강제 종료합니다. TeX 는 `shell_escape=f`, `openin_any=p`, `openout_any=p`, `latexmk -norc` 로 돕니다.
- **AppArmor**: Docker 의 기본 AppArmor 프로필(`docker-default`)이 mount 를 막아 컨테이너 안의 bubblewrap 이 `Failed to make / slave: Permission denied` 로 멈췄습니다(CI, 2026-10-14). 그래서 compose 와 CI 는 일꾼 컨테이너에만 `apparmor=unconfined` 를 줍니다. 바깥층에서 AppArmor 한 겹이 빠지는 대신 seccomp·`cap_drop ALL`·`no-new-privileges`·읽기 전용 루트와 작업마다의 bubblewrap 이 남습니다. mount 만 허용하는 전용 AppArmor 프로필을 만들지는 결정 필요입니다.
- **운영 서버 커널**: Ubuntu 23.10 이상은 AppArmor 가 권한 없는 사용자 이름공간을 막을 수 있습니다(`kernel.apparmor_restrict_unprivileged_userns=1`). 그러면 일꾼 안의 bubblewrap 이 돌지 않습니다. CI 는 이 값을 0 으로 바꾸고 돌립니다. 운영 서버에서 이 값을 바꿀 수 없으면 nsjail 이나 작업별 컨테이너로 가야 합니다(아직 만들지 않음).
- **보관**: 받은 파일은 `DATA_DIR/tex/blobs` 에 내용 해시 이름으로 두고, 그 사용자가 마지막으로 쓴(올리거나 컴파일한) 날부터 `TEX_RETENTION_DAYS` 뒤 지웁니다(30분마다 정리). 만든 PDF 는 `DATA_DIR/tex/out` 에 두고 한 시간 뒤 지웁니다. "이미 올린 파일" 대조는 그 사용자가 올린 것만 봅니다(다른 사람의 파일이 있는지 알 수 없게). 탈퇴하면 그 사용자의 기록을 지우고, 아무도 쓰지 않게 된 파일은 다음 정리 때 지웁니다.
- **원장**: 컴파일마다 `compile_events` 에 엔진·시간·결과·크기·파일 수만 남깁니다(파일 이름·내용 없음).
- **한도**: 사용자당 동시 1개, 서버 전체 동시 `COMPILER_CONCURRENCY`·대기 `COMPILER_QUEUE`, 요금제의 컴파일 한도(위 "요금제와 관리자 도구"). 같은 파일·엔진으로 한 시간 안에 다시 컴파일하면 저장해 둔 결과를 돌려주고 횟수에 세지 않습니다.
- **데모**: `COMPILER=mock` 은 TeX 없이 정해진 규칙으로 작은 PDF·로그를 돌려줍니다(시험·데모용. `\begin{itemise}` 가 있으면 오류).
- **로그인 없는 설치(`AUTH_MODE=none`)**: 모든 사용자가 한 사람으로 취급되어 "올린 파일" 대조·동시 1개·PDF 받기를 함께 씁니다. 신뢰할 수 있는 내부망에서만 쓰세요.

## 역방향 프록시(HTTPS)

서버는 HTTP로 듣고, HTTPS는 앞단의 프록시가 맡습니다. 프록시는 `X-Forwarded-*` 없이도 동작하지만(주소는 `PUBLIC_URL`만 봅니다), 요청 본문 크기 제한은 4MB 이상이어야 합니다(AI 요청).

Caddy 예시(자동으로 HTTPS 인증서를 받습니다):

```
docs.example.com {
    reverse_proxy 127.0.0.1:8787
}
```

nginx 예시:

```nginx
server {
    listen 443 ssl http2;
    server_name docs.example.com;
    # ssl_certificate ... (인증서 설정)
    client_max_body_size 5m;
    location / {
        proxy_pass http://127.0.0.1:8787;
        proxy_set_header Host $host;
    }
}
```

서버가 보안 헤더(CSP, `X-Content-Type-Options`, `Referrer-Policy`, `Cross-Origin-Opener-Policy`, HTTPS일 때 HSTS)를 직접 붙입니다. 프록시에서 덮어쓰지 마세요.
**한글 편집기는 `/rhwp-studio/` 아래에서 같은 주소로 제공**되므로 다른 도메인으로 나눌 필요가 없습니다.

## Docker 없이 실행

Node.js 22.13 이상이 필요합니다.

```bash
npm ci
npm run build                 # 웹 → server/dist/main.js 와 web/dist
cp .env.example .env          # 값을 채운 뒤
set -a; . ./.env; set +a
NODE_ENV=production npm start
```

운영 모드(`NODE_ENV=production`)에서는 서버가 `.env`를 직접 읽지 않으므로, 위처럼 값을 환경에 먼저 넣어야 합니다(개발 모드에서는 `.env`를 자동으로 읽습니다).

서버는 의존성을 포함해 `server/dist/main.js` 하나로 묶여 있고, 웹 파일은 `web/dist`를 읽습니다(`WEB_DIST`로 위치를 바꿀 수 있습니다). SQLite는 Node.js 내장 모듈이라 따로 설치할 것이 없습니다.
systemd로 띄운다면 `EnvironmentFile=`에 `.env`를 지정하고 `ExecStart=/usr/bin/node --disable-warning=ExperimentalWarning server/dist/main.js`를 쓰세요.

## 알려진 한계

- **글꼴**: 한컴·Microsoft의 저작권 있는 글꼴(함초롬, 맑은 고딕 등)은 포함하지 않습니다. 사용자 컴퓨터에 없으면 대체 글꼴로 보이고, 줄바꿈·쪽 나눔이 원본과 다를 수 있습니다. 글꼴 이름은 파일에 그대로 남습니다.
- **한글(HWP·HWPX)**: 편집 화면과 저장은 rhwp가 합니다. rhwp는 아직 모든 문서를 완벽히 다루지는 못합니다(시험 문서 중 하나에서 읽고 다시 저장한 글이 달라진 적이 있습니다). AI 변경을 적용하기 전에 저장했을 때 빠지는 요소가 있는지 검사하고, 있으면 문서를 건드리지 않고 알려 줍니다. 중요한 문서는 원본을 따로 보관하세요.
  - rhwp 저장소의 예제 한글 문서 12개로 열기·서식 점검 제안 적용·내보내기·다시 읽기·되돌리기를 시험했고 글이 달라지거나 사라진 곳은 없었습니다(`web/src/engines/hwp/corpus.test.ts`). 다만 다시 읽는 쪽도 같은 rhwp여서, 한컴오피스에서 같게 열리는지는 확인하지 못했습니다.
  - **코어(rhwp)가 열지 못하는 문서가 있습니다.** rhwp 저장소의 예제 907개 중 `issue2063_huge_cellbreak_table.hwp` 하나는 코어에 문서를 열라고 한 호출이 60초가 지나도 끝나지 않았습니다(Node에서 코어를 직접 불러 확인했고, 브라우저 화면에서는 열어 보지 않았습니다. 같은 코어를 쓰므로 화면이 멈출 수 있습니다). 비밀번호가 걸린 문서 2개는 코어가 비밀번호가 필요하다는 오류를 내고, 앱에는 비밀번호를 입력하는 화면이 없어서 열 수 없습니다.
  - **표 안의 글**: AI 대화·내 규칙은 표 칸 안의 글(표 안의 표 포함)도 읽고 고칩니다. 예제 12개의 표를 빠짐없이 찾고(코어를 직접 걸으며 센 개수와 같습니다), 글이 표 안에만 있던 양식 3개(블로그 양식 7개, `form-002.hwpx` 334개, 중첩 표 문서 1,588개)에서 표 안 글을 읽습니다. 구역이 둘 이상인 문서에서는 코어의 컨트롤 목록(`getControls`)이 둘째 구역부터의 표 안 컨트롤을 빠뜨려서, 그 목록으로 표 안의 표를 미리 가려 찾던 이전 방식은 그런 표를 놓쳤습니다(구역이 둘 이상인 예제 64개 중 7개. 예: `issue5714/1490000-200800034_vietnam_labor_report.hwp`는 표 17개·표 칸 문단 187개). 지금은 모든 표 칸 문단을 직접 살핍니다. 한계는 다음과 같습니다.
    - **서식 점검(문서 안 일관성·기준 문서)은 표 밖 본문만 비교합니다.** 표 칸의 글은 칸마다 서식이 다른 게 보통이라 본문과 묶으면 잘못된 지적이 나옵니다. 표 안의 글은 AI 대화(맞춤법·말투)와 내 규칙으로 고칩니다. AI에게는 서식 규칙을 표를 언급하지 않았다면 표 밖에만 적용하라고 알립니다.
    - **표 안의 표 칸의 문단 서식(정렬·줄 간격)은 바꾸지 못합니다.** 코어(rhwp)가 "중첩 셀의 문단 서식은 아직 다루지 않는다"며 쓰기를 거절합니다(읽기는 목록 번호를 쓰는 함수로 가능하지만, 바꿀 수 없어서 요약에는 넣지 않습니다). 글 바꾸기와 글자 서식(글꼴·크기·굵게 등)은 됩니다. 이런 변경은 적용할 때 이유와 함께 거절됩니다.
    - **"문서에서 보기"는 표 안의 글이면 그 칸(표 안의 표 포함)으로 이동해 고칠 글을 선택합니다.** 한글 편집기의 공개 이동 수단은 본문 문단만 받아서, 빌드할 때 편집기 소스에 "끼워 넣기"만 하는 작은 패치 하나(`web/scripts/build-rhwp-studio.mjs`의 `PATCHES`)를 적용해 편집기 자신의 이동 방식(찾기가 표 칸으로 가는 방식과 같다)을 우리 앱이 부르게 했습니다. 실제 문서의 표 칸 이동은 `e2e/hwp-corpus-reveal.spec.ts`가 확인합니다(이동 뒤 선택된 글이 가리킨 글과 같은지, 선택 표시가 보이는 영역 안에 있는지). 편집기 버전을 올릴 때는 패치 자리를 다시 확인하세요(자리를 하나로 찾지 못하면 빌드가 멈추거나(`RHWP_STUDIO_STRICT=1`) 경고하고, 앱은 표가 있는 곳으로 이동하는 방식으로 돌아갑니다).
    - **문단이 250개를 넘는 아주 큰 표는 칸으로 이동하지 않고 그 표가 있는 곳으로 이동하며 그렇다고 알립니다.** 한 표에 문단이 1,588개 든 예제 문서(`issue1949_giant_cell_nested_tables_perf.hwp`)에서는 칸 안의 글을 선택해 보여 주는 데 약 13초, 캐럿만 옮겨도 칸에 따라 최대 8초가 걸렸고 그동안 편집기와 앱 화면이 멈췄습니다. 다른 문서는 표마다 3~22ms 였습니다. 이 기준(250개)은 두 극단 사이에서 정한 값이고, 그 사이 크기의 표는 재어 보지 못했습니다.

  - **그림·표 캡션**: AI 대화·내 규칙이 읽고 고칩니다. 글 캡션이 달린 그림(본문 문단·표 칸·글상자 안 어느 깊이든)과 본문 문단에 바로 놓인 표의 캡션 글을 읽고, 글 바꾸기·글자 서식·문단 서식(본문 문단에 바로 놓인 그림·표의 캡션만)·되돌리기를 합니다. 카드에는 "그림 캡션 1"(캡션이 달린 그림을 문서 순서로 센 번호)과 "표 2 캡션"(표 칸의 "표 2 · 3행 1열"과 같은 표 번호)이 적힙니다. 조사 내용과 수치는 [docs/CAPTION.md](CAPTION.md)에 있습니다. 확인한 것과 한계는 다음과 같습니다.
    - **캡션 안의 자동 번호("그림 1"의 1)는 글이 아니라 번호 컨트롤이고, 코어는 그 자리를 위치 정보 없이 공백 한 글자로만 보여 줍니다.** 그대로 두면 AI 가 "공백이 셋"을 고치자고 할 수 있어서, 글의 모양(라벨 뒤 공백 덩어리의 둘째 글자)으로 그 자리를 어림해 AI 에게는 `№`로 보여 주고, 그 자리와 둘레 공백을 건드리는 변경은 이유와 함께 거절합니다(한 묶음이면 묶음 전체가 취소됩니다). 어림은 번호 컨트롤이 든 캡션 492개에서 모두 맞았습니다(내보낸 HWPX 의 XML 과 대조. 번호 자리 글자는 모두 일반 공백). 번호 없이 공백을 연달아 쓴 캡션은 번호 자리로 보일 수 있고, 그때는 그 공백을 바꾸는 변경이 거절될 뿐입니다.
    - **CI에서 도는 시험**: 만든 HWP·HWPX 문서에서 읽기·위치·순서(표 캡션 위·아래), 글 바꾸기·글자 서식·문단 서식과 되돌리기, 내보낸 HWPX 에서 번호 컨트롤이 라벨 뒤·글 앞에 그대로 있는 것, 번호 자리를 건드리는 변경 8가지의 거절(`web/src/engines/hwp/caption.test.ts` 33개. 번호 자리 보호를 끄면 거절 시험이 모두 실패하는 것을 확인했습니다). 실제 앱에서 맞춤법 제안 적용(HWP·HWPX)·되돌리기, 내 규칙에 "캡션"을 적었을 때만 캡션 글자 크기가 바뀌는 것, 서식 점검이 캡션을 본문과 비교하지 않는 것, "문서에서 보기"(`e2e/hwp-caption.spec.ts` 8개. 내려받은 파일을 코어를 직접 걸으며 읽어 확인합니다). 예제 12개에서 그림·표 캡션의 개수와 글을 코어를 직접 걸으며 읽은 것과 맞춰 봅니다(`corpus.test.ts`).
    - **rhwp 저장소의 예제 전체로도 확인했습니다**(이 환경에서 한 번 해 본 것이며 CI에서는 돌지 않습니다). 열 수 있는 900개 모두에서 그림·표 캡션의 개수와 글(번호 표지를 공백으로 되돌려 견줌)이 코어를 직접 걸으며 읽은 것과 같았습니다. 캡션이 달린 그림·표가 든 69개 문서 중 읽을 글이 있는 58개에서 캡션 문단 665개(그림 68개, 표 574개의 캡션)를 읽었고, 그중 585개의 끝 두 글자를 한 번에 `ZZ`로 바꿔 내보냈다 다시 읽었더니 모두 맞았고(저장 손실 0), 되돌리면 처음과 같았으며, HWPX 로 내보내 센 자동 번호(`autoNum`) 컨트롤 수(합계 568)가 고치기 전·후·되돌린 뒤에 같았습니다.
    - **읽지 못하는 캡션이 있습니다**: 표 칸·글상자 안에 놓인 표의 캡션(코어의 경로 함수가 표 캡션을 가리키는 칸 번호를 받아들이지 않습니다)과 도형·묶음 개체의 캡션. 예제 900개에서 XML 의 캡션 707개 중 674개(95%)를 읽고, 읽지 못하는 33개(표 칸·글상자 안의 표 24개, 도형·묶음 개체 9개)는 17개 문서에 있습니다. 읽지 못하는 글은 AI 에게 넘기지 않고 고치지도 않습니다.
    - **"문서에서 보기"**: 편집기가 그 캡션으로 이동합니다. 다만 코어가 캡션의 자동 번호를 그리기 전에 글 속에 글자로 끼워 넣어서, 편집기의 글자 위치가 번호 뒤에서 번호의 글자 수만큼 어긋납니다(실제 편집기에서 번호 뒤의 글을 선택하면 한 글자 앞으로 밀려 엉뚱한 글이 선택되는 것을 확인했습니다). 그래서 번호 뒤의 글은 선택하지 않고 번호 앞에 캐럿만 두며 그렇다고 알립니다. 라벨(번호 앞)과 번호 없는 캡션의 글은 정확히 선택합니다.
    - **문단 서식(정렬·줄 간격)은 본문 문단에 바로 놓인 그림·표의 캡션만 바꿉니다.** 표 칸·글상자 안에 놓인 그림의 캡션은 이유와 함께 거절합니다. 서식 점검(문서 안 일관성·기준 문서)은 본문만 비교하고, AI 에게는 서식 규칙을 "캡션"을 언급하지 않았다면 캡션에 적용하지 말라고 알립니다(맞춤법·말투 교정은 모두 적용합니다).
    - 코어는 메모리에서 만든 문서의 표 캡션을 내보냈다 다시 열면 글 끝에 공백을 하나 붙입니다(왕복해도 더 늘지 않고, 예제 문서의 캡션은 왕복해도 같았습니다). 고쳐 내보낸 파일의 캡션이 한컴오피스에서 같게 열리는지는 확인하지 못했습니다(다시 읽는 쪽도 같은 rhwp입니다).
- **Word(DOCX)**: 저장은 SuperDoc이 만든 DOCX입니다. 원본과 파일 안의 XML 표기(요소 순서 등)가 달라질 수 있습니다. LibreOffice 24.2로는 확인했습니다(LibreOffice가 만든 표 있는 단순 문서를 고쳐 내려받은 파일이 열리고, 고친 두 줄 말고는 글이 같고, PDF로도 변환됩니다. `e2e/interop.spec.ts`). Microsoft Word·한컴오피스에서 열었을 때의 호환은 확인하지 못했습니다. 되돌리기는 화면에 보이는 모양을 원래대로 돌리며, 파일 안의 서식 표기 방식은 달라질 수 있습니다.
  - **AI가 다루는 범위**: 본문, 표 안의 글(표 안의 표 포함), 머리말·꼬리말, 각주·미주, 글상자. 카드에는 표 번호·행·열 또는 "머리말", "꼬리말(첫 쪽)", "각주 1", "글상자 2"처럼 위치가 적힙니다. 칸을 가로·세로로 합친 표도 SuperDoc 화면에서 시험했습니다(`e2e/docx-table.spec.ts`).
  - **서식 점검(문서 안 일관성·기준 문서)은 한글 문서와 같이 본문(표 밖)만 비교합니다.** 표 칸·머리말·꼬리말·각주의 서식은 본문과 다른 게 보통이라, 섞으면 양식의 제목 칸이나 머리말이 본문과 다르다는 잘못된 지적이 나옵니다(표 칸은 실제 SuperDoc 화면에서 이 오탐을 재현해 확인한 뒤 고쳤습니다).
  - **머리말·꼬리말·각주·미주**: SuperDoc 문서 API가 본문 밖의 글을 "이야기(story)" 단위로 읽고 고치게 해 줍니다. 글·글자 서식·문단 서식을 모두 바꾸고 되돌리며, 실제 SuperDoc 화면에서 확인했습니다(`e2e/docx-area.spec.ts` 11개: 맞춤법 제안 적용·되돌리기, 내 규칙으로 머리말 글자 크기 바꾸기, 미주, "문서에서 보기"). 내려받은 파일을 LibreOffice로 다시 열어 쪽 번호 필드와 각주·미주 표시가 그대로인 것도 확인했습니다(`e2e/interop.spec.ts`의 두 번째 시험. LibreOffice가 만든 머리말·꼬리말·각주·미주 문서를 씁니다).
    - **각주 번호는 본문에서 각주 표시가 나오는 순서로 셉니다.** 편집기가 알려 주는 번호는 파일 안의 번호(w:id)라서, LibreOffice가 만든 문서처럼 번호가 2부터 시작하면 화면에 보이는 번호와 다릅니다(실제 LibreOffice 문서로 확인하고 고쳤습니다). 쪽·구역마다 번호를 다시 매기는 설정은 반영하지 않습니다.
    - 머리말·꼬리말은 구역마다 따로 쓰는 경우에만 "· 구역 N"이 붙고(그 머리말을 처음 지정한 구역), 어느 구역도 쓰지 않는 머리말은 읽지 않습니다. 홀수·짝수 쪽 머리말을 따로 쓰는 문서는 기본 머리말이 "홀수 쪽"으로 적힙니다.
    - 표나 내용 컨트롤로 짠 머리말·꼬리말은 칸 안의 문단까지 읽습니다. 칸 안에 각주 표시·탭 같은 글이 아닌 것이 끼어 있으면 글자 위치가 어긋날 수 있어 그 문단은 읽지 않습니다.
    - 본문 밖에서 읽는 문단은 500개까지입니다. 각주가 많은 문서는 읽는 데 시간이 걸립니다(이 환경의 실제 SuperDoc에서 각주 150개 문서는 요약이 약 0.4초, 각주 150곳을 한 번에 고치는 데 약 7초였습니다).
    - 쪽 번호 필드의 결과(예: 1)도 글로 읽힙니다. 이것을 바꾸는 제안은 의미가 없습니다(Word가 쪽 번호를 다시 계산합니다).
  - **글 속의 각주 표시·그림 자리(`￼`)를 바꾸는 글 바꾸기는 거절합니다.** 실제 SuperDoc에서 이 자리를 지우면 각주 내용까지 함께 지워지는 것을 확인했습니다(본문의 각주 표시도 마찬가지로 보호합니다). AI에게도 이 문자를 `find`·`replace`에 넣지 말라고 알립니다.
  - **글상자 안의 글**: AI 대화·내 규칙이 읽고 고칩니다. 글·글자 서식·문단 서식을 모두 바꾸고 되돌립니다. 편집기(SuperDoc)가 글상자를 번호(`tb0`, `tb1` …)로 가리키는 이야기(story)로 열어 주고, 본문 문단 목록에는 글상자 안의 문단이 글상자를 단 문단 바로 다음에 나옵니다. 우리는 그 문단에 글상자 자리만 붙여서 문단 번호는 그대로입니다. 카드에는 문서에 나오는 순서대로 센 "글상자 2"가 적힙니다. 실제 SuperDoc 화면에서 확인한 것과 한계는 다음과 같습니다(`e2e/docx-textbox.spec.ts` 11개).
    - **확인한 것**: 맞춤법 제안 적용·되돌리기, 내 규칙으로 글상자의 글자 크기 바꾸기·되돌리기, 본문 문단에 놓인 글상자와 표 칸 안의 문단에 놓인 글상자, 글상자 하나에 문단이 둘인 경우, 옛 방식(VML)으로만 저장된 글상자(`mc:AlternateContent` 없이 `w:pict`만 있는 것. 읽고 고치며 파일에도 옛 방식 그대로 남습니다), 내려받은 파일의 글상자 안 글. 글상자 안의 글은 문단 번호가 같은 문단 목록에 나오지만 본문 문단 주소로는 고칠 수 없어서(편집기가 "Block … not found"를 냅니다) 글상자 번호로 가리켜 고칩니다.
    - **Word·LibreOffice는 글상자를 그림 방식(DrawingML)과 옛 방식(VML) 두 벌로 저장합니다**(`mc:AlternateContent`). 편집기는 그림 방식 쪽만 받아들이고 옛 방식 복사본은 비어 있는 번호로 건너뛰므로(실제 LibreOffice 문서에서 `tb0`, `tb2` … 로 나왔습니다) 번호를 하나씩 찾되 빈 번호가 세 개 이어지면 그만두고, 최대 300번까지 찾습니다. 글을 고쳐 내려받으면 두 벌 모두 고쳐져 있는 것을 확인했습니다. **빈 번호가 세 개를 넘게 이어진 뒤에 나오는 글상자는 찾지 못합니다.** 그런 문서는 만나지 못했고 일부러 만들어 보지도 않았습니다.
    - **머리말·꼬리말 안의 글상자는 읽지 않습니다.** 머리말 안의 글상자로 시험했습니다. 머리말의 글은 고쳐지고, 글상자 안의 글은 AI에게 넘기지 않으며 파일에도 그대로 남습니다(두 벌 모두). 꼬리말도 같은 구조이지만 시험하지 않았습니다. 도형을 묶은 글상자, 글상자 안의 글상자, 도형의 글(`wps:txbx`가 아닌 것)은 시험하지 못했습니다. 편집기가 열지 못해 목록에서 빠지는 글상자의 글은 AI에게 넘기지 않습니다(안내문에도 적혀 있습니다).
    - **서식 점검(문서 안 일관성·기준 문서)은 본문만 비교합니다.** 글상자의 서식은 본문과 다른 게 보통이라 섞으면 잘못된 지적이 나옵니다. AI에게는 서식 규칙을 "글상자"를 언급하지 않았다면 본문에만 적용하라고 알립니다(맞춤법·말투 교정은 모두 적용합니다).
    - **글상자가 많은 문서는 느립니다.** 글상자 번호를 하나씩 조회하기 때문입니다. 이 환경의 실제 SuperDoc에서 글상자 안에 오탈자가 하나씩 든 문서를 맞춤법으로 요청해 제안 카드가 뜰 때까지 걸린 시간은 글상자 0개 0.6초, 30개 2.3초, 100개 약 15초였고, 그 제안(30곳·100곳)을 전체 적용하는 데는 각각 약 3.8초, 약 33초였습니다. 편집기가 같은 번호 목록으로 다시 읽는 일은 문단 번호가 바뀌지 않는 동안 되풀이하지 않게 했습니다(그 전에는 100개 문서의 전체 적용이 약 48초였습니다). 남은 시간이 어디에 쓰이는지는 재어 보지 않았습니다(고칠 곳이 100곳이라 편집기가 글을 하나씩 고치는 시간이 클 것으로 짐작합니다). 글상자 100개는 흔한 문서가 아니고, 이 값들은 한 번씩 잰 값입니다.
  - **"문서에서 보기"**: 편집기가 그 쪽을 그리고 있으면 머리말·꼬리말·각주·글상자 안의 글도 문서 위에 강조하고 그 곳으로 이동합니다. 편집기가 쪽에 그리지 않는 미주는 이동하지 못하고 그렇다고 알립니다. 표 칸 안의 문단에 놓인 글상자는 시험한 문서에서 편집기가 글의 자리를 알려 주지 못해 강조하지 못했고, 대신 "이 글은 글상자 2에 있어요…"라고 알립니다(글상자가 문서 위에 그려지는 것은 화면으로 확인했습니다).
- **LaTeX**(M2 편집·컴파일, M3 AI 제안. 2026-10-14 이 환경에서 확인한 것이며, 진짜 TeX 시험과 탈출 시험은 CI 의 `latex` 작업에서만 돈다):
  - 컴파일 일꾼 이미지는 이 개발 환경에서는 만들지 못했고(Docker Hub 가 기본 이미지 요청에 429 를 돌려줌) CI 에서만 만들었습니다. 이미지의 TeX Live 는 Debian bookworm 패키지(TeX Live 2022)로 정했고, 설계의 `install-tl` 연도 스냅숏으로 바꿀지는 결정 필요입니다. 이미지 크기는 CI 에서 1.34GB 였습니다(`docker image ls`, 2026-10-14).
  - 대신 이 기계(Ubuntu 24.04, TeX Live 2023 패키지, root, AppArmor 없음)에서 일꾼을 직접 띄워 확인했습니다: 탈출 시험 12개 통과(`compiler/test/escape/run.ts`), bubblewrap 을 끄면 1개(LuaTeX `io.open('/etc/passwd')`), TeX 설정(`shell_escape`·`openin_any`·`openout_any`)을 풀면 2개(`\write18`, LuaTeX `os.execute` — 둘 다 작업 폴더 안에만 파일이 생김)가 실패해 두 겹이 따로 막는 것을 봤습니다. 컨테이너 안(읽기 전용 루트, `cap_drop ALL`, seccomp 프로필, `apparmor=unconfined`, 권한 없는 사용자, 네트워크 없음)에서는 CI 의 `latex` 작업이 같은 탈출 시험 12개와 `e2e/tex-real.spec.ts` 를 통과했습니다(2026-10-14, 일꾼 이미지의 TeX Live 2022). 이 CI 러너는 `kernel.apparmor_restrict_unprivileged_userns=0` 으로 바꾸고 돌립니다.
  - 템플릿 4개를 진짜 TeX 로 컴파일한 시간은 0.9–9.2초였습니다(`templates/latex/README.md`). 한국어 템플릿 PDF 를 `pdftotext` 로 읽으면 한글 구절 4개가 원문과 같았습니다(`e2e/tex-real.spec.ts`).
  - 오류가 있으면 PDF 를 돌려주지 않습니다(TeX 가 오류를 넘기고 만든 PDF 도 버림). 마지막으로 성공한 PDF 는 화면에 남겨 둡니다.
  - 로그의 경고가 어느 파일에서 났는지는 로그의 괄호를 따라가 찾는데, **공백이 든 파일 이름은 따라가지 못합니다**(오류는 `-file-line-error` 의 파일:줄을 그대로 써서 영향 없음).
  - EPS→PDF 자동 변환(제한된 셸 실행)은 꺼져 있습니다. biber 의 원격 자료(`location=remote`)는 네트워크가 없어 안 됩니다(시험하지 않음).
  - Windows 에서 만든 ZIP 의 한글 파일 이름(CP949, UTF-8 표시 없음)은 깨져 보일 수 있습니다(UTF-8 로 읽히지 않으면 latin1 로 읽음). ZIP64(4GB 넘는 ZIP)는 열지 않습니다.
  - **한글 입력기(IME)로 원고에 한글을 치는 것은 손으로 확인하지 못했습니다**(Playwright 의 입력은 입력기를 거치지 않음). 데스크톱 크롬·사파리, 휴대폰 모두 "확인 못 함"입니다.
  - SyncTeX(원고↔PDF 위치 이동), 컴파일 중간 파일 재사용, 실시간 공동 편집은 없습니다(M7).
  - **AI 제안(M3)은 데모 AI 로만 시험했습니다.** 진짜 Claude 의 제안이 서버 검증에서 얼마나 버려지는지(탈락률), 오류 고치기를 적용한 뒤 컴파일이 성공하는 비율은 재지 못했습니다(API 키 없음). AI 에는 `.tex`·`.bib` 원고만 보내고 verbatim·lstlisting·minted 안의 글은 보내지 않습니다. 대화는 본문 글만 고치고(수식·라벨·참조·인용 키·명령·서문·주석은 바꾸지 않음, 지시에 수식이 있으면 수식은 허용), 오류 고치기는 오류 근처(±2 블록)와 서문만 고칩니다. 고친 원고가 컴파일되는지는 서버가 미리 확인하지 않습니다(다시 컴파일해 오류가 늘면 화면이 알림).
- **PDF**: 보기만 됩니다. 한글 문서의 PDF 저장은 한글 편집기의 인쇄 창을 엽니다(브라우저가 PDF로 저장). Word 문서의 PDF 저장은 아직 없습니다.
- **휴대폰**: Chromium 에뮬레이션(Pixel 7)으로 화면 배치와 단추 크기를 시험했습니다. 실제 기기(터치 입력, 한글 입력기, 가상 키보드)에서는 시험하지 못했습니다. Word 편집기의 도구는 영어 보조 문구(접근성 라벨 등)가 일부 남아 있습니다.
- **AI**: 제안이 문서에 맞는지 서버가 걸러 주지만, 제안의 **내용이 옳은지**는 보장하지 못합니다. 그래서 항상 사용자가 적용 여부를 정합니다.

## 문제 해결

| 증상 | 확인할 것 |
| --- | --- |
| "이 서버에는 한글 편집기가 설치되어 있지 않아요" | 빌드 기록에서 "한글 편집기" 경고를 찾으세요. 빌드하는 곳이 GitHub에 못 나갔을 가능성이 큽니다. `RHWP_STUDIO_STRICT=1`로 빌드하면 그때 멈춰 알려 줍니다. |
| 구글 로그인 후 `/?login=failed` | 승인된 리디렉션 URI가 `{PUBLIC_URL}/api/auth/callback`과 정확히 같은지, `PUBLIC_URL`이 사용자가 실제로 접속하는 주소인지 확인하세요. 서버 기록에 실패 이유가 남습니다. |
| "AI 서비스 인증에 문제가 있어요" | `ANTHROPIC_API_KEY`가 맞는지, 키에 해당 모델을 쓸 권한이 있는지 확인하세요. |
| "이 서버에는 AI가 연결되어 있지 않아요" | `AI_PROVIDER`와 키를 확인하세요. 키가 없으면 서버가 켜질 때 경고를 남깁니다. |
| 서버가 켜지자마자 멈춤 | 출력된 설정 문제 목록을 읽으세요(필수 값 누락, 잘못된 AI 설정 파일 등). |

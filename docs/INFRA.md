# 운영 기반(인프라) 설계

AllDoc 을 공개 서비스로 띄우는 데 필요한 것을 정리한 **설계**입니다. 다루는 것은 서버, 서버 밖 백업, 감시, 메일, 배포, 비밀값 관리입니다.
**이 문서의 내용은 아직 구현하지 않았고, 실제로 띄운 서버도 없습니다.**
관련 문서:
- 제품화 순서(계정·요금제·결제): `docs/PRODUCT.md`
- 컴파일 일꾼: `docs/LATEX.md`
- 지금 할 수 있는 배포 방법: `docs/DEPLOY.md`

전제(2026-10 사용자 결정, `docs/PRODUCT.md` 와 같음):
- 첫 고객은 **국내 개인**입니다.
- **사업자등록은 아직 없습니다.** 가입·결제에 사업자가 필요한 서비스는 지금 쓸 수 없습니다.
- **AGPL-3.0 오픈소스를 유지**합니다. 이 문서와 저장소에는 비밀값을 적지 않습니다.

표기:
- **확인함**: 이 문서를 쓰며 저장소 코드나 공식 페이지에서 직접 본 것입니다. 가격에는 출처와 확인 날짜를 붙입니다.
- **확인 필요**: 공식 자료로 확인하지 못한 것입니다.
- **가정**: 계산하려고 둔 값입니다. 실측이 아닙니다.
- **직접 셈**: 공식 시간당 단가에 730시간을 곱하는 식으로 이 문서에서 계산한 값입니다.

## 1. 현재 상태

기준은 `claude/latex-m2` 브랜치의 코드입니다(2026-10-15). M0~M3 이 구현된 상태입니다.

| 영역 | 있는 것(코드에서 확인함) | 계획만 있는 것 | 빠진 것 |
| --- | --- | --- | --- |
| 로그인·계정 | 구글 OAuth(PKCE)(`server/src/auth/google.ts`). 서명 쿠키(30일, `SESSION_TTL_SEC`)에 세션 버전을 넣고 요청마다 `users` 를 조회(`server/src/auth/{session,accounts}.ts`). 탈퇴(`server/src/auth/deletion.ts`), 약관 동의(`TERMS_VERSION`) | — | 실제 구글 계정으로 끝까지 해 본 확인 |
| DB | SQLite(`node:sqlite`) `${DATA_DIR}/alldoc.sqlite`, WAL. 번호 붙은 마이그레이션은 `PRAGMA user_version` 으로 관리하고, 파일이 서버보다 새 판이면 시작을 거부(`server/src/db/index.ts`). 테이블: 계정, 사용 횟수, AI·컴파일 원장, 요금제 부여, 관리 기록 | Postgres(조건이 생기면, 아래 4장) | — |
| 요금제·한도 | 요금제 파일(`PLANS_CONFIG_PATH`)과 관리자 수동 부여(`server/src/billing/entitlements.ts`, `server/src/admin.ts`). 하루·월 횟수, 글자 상한, 월 원가 상한, 전체 하루 비용 차단기(`AI_DAILY_BUDGET_USD`) | 결제(M5) | — |
| 백업 | 서버가 하루 한 번 `VACUUM INTO` 로 `BACKUP_DIR`(기본 `/data/backups`)에 스냅숏을 만들고 `BACKUP_KEEP`(기본 14)개를 남김(`server/src/backup.ts`). 개발 환경에서 복구 훈련 1회(`docs/DEPLOY.md` "백업") | — | **서버 밖 복사**(같은 디스크에만 있음). Docker 볼륨과 서버 밖 복사를 포함한 복구 훈련 |
| 컴파일 일꾼 | `compiler/` 이미지(CI 에서 1.34GB), compose `compiler` 서비스(profile `latex`). 격리: 내부망(`internal: true`), 읽기 전용 루트, tmpfs, `cap_drop: ALL`, `no-new-privileges`, `compiler/seccomp.json`, `apparmor=unconfined`, `pids_limit`·`mem_limit: 4g`·`cpus: 2`. 작업마다 bubblewrap 을 씀. 앱과는 HMAC(`COMPILER_SECRET`)으로 이야기함. | 배포 틀 | 2단계 Dockerfile(`node:22-bookworm` → `node:22-bookworm-slim`, `node` 사용자, `/data` 볼륨, `HEALTHCHECK` 가 `/api/health` 호출), `docker-compose.yml`, Caddy·nginx 예시(`docs/DEPLOY.md`) | — | 호스팅·도메인·HTTPS 실제 구성. 이미지 레지스트리 |
| CI | `.github/workflows/ci.yml`(`test`·`no-docx`·`docker`), `.github/workflows/latex.yml`. 이미지는 CI 안에서 만들고 버림 | — | 레지스트리에 올리기, 서버 반영, 되돌리기 |
| 비밀값 | 환경 변수로만 받음(`server/src/config.ts`). 일꾼은 `COMPILER_SECRET` 만 받고 읽은 뒤 환경에서 지움(`compiler/src/main.ts`) | `BILLING_*`, `BILLING_ENC_KEY`(M5) | 보관 위치, 교체 절차. 세션 비밀이 하나라서 바꾸면 모두 로그아웃 |
| 남용 방지 | 사용자 기준: 요금제 한도, AI 사용자당 동시 1개(`inflight`), 컴파일 사용자당 동시 1개와 서버 전체 동시·대기 상한(`COMPILER_CONCURRENCY`·`COMPILER_QUEUE`), AI 본문 4MB 상한, 같은 출처 검사(`sameOriginOnly`) | — | **IP 기준 요청 제한.** 앱은 접속 IP 를 읽지 않음(`X-Forwarded-For` 를 쓰는 곳이 없음) |
| 감시·로그 | `console.log` 한 줄 기록(문서 글은 남기지 않음, `docs/AI.md`). 컨테이너 `healthy` 표시. `/api/health` 는 `{ ok: true }` 만 돌려줌 | — | 오류 추적, 바깥 가동 감시, 디스크·메모리 경보, 백업 성공 감시, 로그 보관 기간 |
| 메일 | 없음 | 결제 안내·만료 예고(M5) | 발송 서비스, 발신 도메인 인증 |

## 2. 구성도

```
                사용자 브라우저 (문서는 IndexedDB. LaTeX 는 컴파일할 때만 파일을 보냄)
                        │ HTTPS 443
                        ▼
   ┌──────────── VM 한 대 (베타) ─────────────────────────────────────────┐
   │  Caddy ── HTTPS·인증서 자동 갱신, IP 기준 요청 제한, 접속 기록          │
   │    │ http 127.0.0.1:8787                                            │
   │    ▼                                                                │
   │  앱 alldoc ── /data 볼륨: alldoc.sqlite, backups/, tex/              │
   │    │                         │                                      │
   │    │ compile 망(internal)    └─ 백업 일꾼(/data/backups 읽기 전용) ───┼──► 서버 밖 백업 저장소
   │    ▼     HMAC 서명                                                   │
   │  compiler ── tmpfs 만, 비밀값은 COMPILER_SECRET 하나, 바깥 연결 없음   │
   └─────────────────────────────────────────────────────────────────────┘
      앱이 바깥으로: Anthropic API(미국) · 구글 OAuth · 메일 발송 · 오류 추적
      바깥에서 안으로: 가동 감시 → https://<도메인>/api/health
```

| 요소 | 하는 일 | 갖는 비밀값 | 갖는 데이터 | 바깥 연결 |
| --- | --- | --- | --- | --- |
| 역방향 프록시(Caddy) | HTTPS 종료, 인증서 자동 갱신, IP 기준 요청 제한, 접속 기록 | TLS 개인키(자동 발급) | 접속 기록(IP·경로·상태 코드). 본문은 남기지 않음 | 인증서 발급(ACME) |
| 앱 서버(`alldoc`) | 로그인, 한도, AI 중계, 컴파일 대기열, 정적 파일, 하루 스냅숏 | `SESSION_SECRET`, `ANTHROPIC_API_KEY`, `GOOGLE_CLIENT_SECRET`, `COMPILER_SECRET`, 앞으로 `BILLING_*`·`BILLING_ENC_KEY`, 메일·오류 추적 키 | `/data/alldoc.sqlite`(계정·이메일·사용 횟수·원장·요금제 부여·관리 기록), `/data/backups`, `/data/tex`(컴파일하려고 받은 파일, `TEX_RETENTION_DAYS` 동안) | Anthropic, 구글, 메일, 오류 추적, 결제(M5) |
| 컴파일 일꾼(`compiler`) | LaTeX 컴파일 | `COMPILER_SECRET` 하나(읽은 뒤 환경에서 지움) | 작업 중인 파일만(tmpfs) | **없음**(내부망만) |
| 백업 일꾼(새로) | 스냅숏을 암호화해 서버 밖으로 복사 | 백업 저장소 키, 백업 암호 | 암호화된 스냅숏 | 백업 저장소 |
| 서버 밖 백업 저장소 | 스냅숏 보관 | — | 암호화된 DB 스냅숏(복호 키는 저장소 밖) | — |
| 메일 발송 서비스 | 거래 메일 | — | 받는 사람 주소, 메일 본문(문서 글은 넣지 않음) | — |
| 오류 추적 | 예외 수집 | — | 오류 종류·스택·경로. **요청 본문·문서 글·AI 응답은 보내지 않음** | — |

- 컴파일 일꾼에게 다른 비밀값을 주지 않는 것은 `docs/LATEX.md` 의 원칙이고, compose 가 이미 그렇게 되어 있습니다(`.env` 를 넘기지 않음).
- 백업 일꾼은 앱 컨테이너와 따로 둡니다. 앱이 뚫려도 백업 저장소 키가 드러나지 않게 하기 위해서입니다. 백업 저장소 키에는 **쓰기만 되고 지우기는 안 되는 권한**을 줍니다. 그러면 서버가 뚫려도 지난 백업은 지울 수 없습니다(저장소마다 되는지 확인 필요).
- `/data/tex` 의 컴파일 파일은 백업하지 않습니다. 브라우저에 원본이 있고, 보관 기간(기본 7일)이 짧은 임시 파일이기 때문입니다. M6(서버 저장)를 넣으면 다시 정합니다.

## 3. 호스팅 비교와 추천

### 확인한 방법과 한계

가격은 2026-10-15 에 공식 자료에서 읽었습니다.
- **AWS**: 공개 가격 파일(`pricing.us-east-1.amazonaws.com`의 ap-northeast-2 파일)
- **GCP**: 가격 페이지의 서울(asia-northeast3) 값
- **Fly.io·Railway**: 공식 문서 저장소의 원문(GitHub, 2026-10-14 커밋)

다음 업체는 이 문서를 쓴 환경의 네트워크에서 사이트가 열리지 않아 **아무 값도 확인하지 못했습니다**.
- 국내: 네이버클라우드(ncloud.com), KT 클라우드, NHN Cloud
- 저가 VM: Vultr, Hetzner, DigitalOcean, Akamai(Linode)
- PaaS: Render

이 업체들은 표에 "확인 필요"로 두었고, **이 업체들이 더 싸거나 더 나을 수 있습니다**. 출시 전에 직접 가격표를 보고 이 장을 고칩니다.

### 비교 기준별 판단

- **한국 사용자 지연**
  - 서울 리전을 가진 곳(AWS·GCP·국내 클라우드·Oracle)이 유리합니다.
  - Fly.io(도쿄)와 Railway(싱가포르)는 한 번 더 멀어집니다.
  - 다만 이 앱은 편집을 브라우저가 하고, 서버 왕복은 AI(수 초~수십 초)와 컴파일(초 단위)이 대부분입니다. 그래서 지연 차이가 체감에 주는 영향은 작다고 봅니다(**재지 않았습니다**).
- **컴파일 격리**
  - 일꾼은 세 가지가 필요합니다(`docs/LATEX.md`, `docs/DEPLOY.md` "LaTeX 컴파일").
    - 컨테이너 안에서 bubblewrap 이 사용자 이름공간을 만들 수 있어야 합니다.
    - 일꾼 전용 seccomp 프로필(`compiler/seccomp.json`)을 쓸 수 있어야 합니다.
    - 일꾼 컨테이너에만 AppArmor 를 풀 수 있어야 합니다.
  - 가능하면 gVisor(`runsc`)도 씁니다.
  - **VM**: Docker 데몬을 직접 띄우므로 셋 모두 운영자가 정합니다.
    - 커널 값(`kernel.apparmor_restrict_unprivileged_userns`)과 runsc 설치도 운영자가 합니다.
    - 다만 gVisor 와 bubblewrap 을 겹쳐 쓸 수 있는지(gVisor 안에서 사용자 이름공간을 만드는 것)는 확인하지 못했습니다(E3 후속).
  - **PaaS**: 컨테이너 실행 옵션(seccomp·AppArmor·런타임)을 사용자가 정할 수 없는 것이 보통입니다.
    - Railway 는 비특권 컨테이너라고 문서에 적혀 있습니다.
    - Fly.io 는 문서에 언급이 없습니다.
  - 그래서 **PaaS 는 일꾼의 두 겹 격리를 확인된 방법으로 세울 수 없습니다.**
- **SQLite 와 영구 디스크**
  - 앱은 디스크 위의 파일 하나를 한 프로세스가 씁니다.
  - VM 과 Fly.io·Railway 의 볼륨은 이 구조에 맞습니다.
  - Cloud Run 은 맞지 않습니다.
- **국외 이전 고지**
  - AI 를 쓰면 문서 글이 Anthropic(미국)으로 가므로, **어느 호스팅을 고르든 개인정보처리방침에 국외 이전 항목이 필요합니다**(`docs/PRODUCT.md` 점검표).
  - 서버를 해외 리전(도쿄·싱가포르)에 두면 계정 정보(이메일)도 국외 이전 항목에 들어갑니다.
  - 개인정보 보호법 제28조의8 제1항은 국외로 "제공(조회되는 경우를 포함한다)ㆍ처리위탁ㆍ보관"하는 것을 모두 "이전"으로 봅니다. 처리방침에 공개해야 할 항목은 제2항에 있습니다: 항목, 국가·시기·방법, 받는 자, 이용 목적·보유 기간, 거부 방법과 효과.
    - 이 조문은 law.go.kr 을 열지 못해, law.go.kr 자료를 옮긴 비공식 저장소(legalize-kr)에서 읽었습니다. 그 파일은 시행일이 2027-03-09 인 개정본이라 지금 시행 중인 조문과 다를 수 있습니다(**확인 필요**).
  - 해외 회사의 서울 리전에 두는 것이 국외 이전에 해당하는지는 **법률 확인 필요**입니다. 국내에 저장하지만 해외에서 "조회"될 수 있기 때문입니다.
  - 그래도 서울 리전을 쓰면 적어도 저장 위치는 국내라고 적을 수 있습니다.
  - 해외 서비스(Sentry 미국·EU, R2, 해외 메일 서비스)를 쓰면 각각 국외 이전 항목이 하나씩 늘어납니다.
- **백업·스냅숏**
  - VM 업체는 모두 디스크 스냅숏이 있습니다(가격은 위 표).
  - 다만 스냅숏은 같은 업체 안에 남습니다. 그래서 계정 정지·삭제 같은 사고에 대비해 **DB 스냅숏은 다른 곳으로도 복사**합니다(4장).
- **사업자 없이 가입·결제**: 모든 후보가 확인 필요입니다. 가입 화면에서 개인 계정·개인 카드로 되는지 보고 고릅니다.

### 추천

**베타는 AWS Lightsail 서울 리전 VM 한 대를 권합니다.** 확인된 값 안에서 고른 것이고, 국내 클라우드·저가 VM 가격을 확인하면 다시 견줍니다.
- **가격**: 이번에 확인한 서울 리전 VM 중 가장 쌉니다. 2 vCPU·4GB·80GB 에 공인 IPv4·전송량이 포함되어 약 $23.5/월입니다(직접 셈).
  - EC2(t4g.medium)는 디스크·IPv4 를 따로 내서 더 비쌉니다.
  - GCP e2-medium 은 디스크 없이 $31.38 입니다.
- **격리**: VM 이라 일꾼의 seccomp·AppArmor·커널 설정·gVisor 를 운영자가 정할 수 있습니다. PaaS 는 이것이 확인되지 않았습니다.
- **지연·고지**: 서울 리전이라 지연이 짧고, 저장 위치를 국내로 적을 수 있습니다.
- **백업**: 같은 업체의 S3(서울, 처음 50TB 까지 $0.025/GB·월)를 서버 밖 백업 저장소로 쓸 수 있습니다. 다른 업체 저장소를 하나 더 두는 것은 4장을 봅니다.
- **나중에 옮기기**: 성장하면 EC2 로 옮기거나 같은 Lightsail 의 큰 묶음으로 올릴 수 있습니다. 스냅숏으로 새 VM 을 만드는 방식이 Lightsail 에 있는지는 확인 필요입니다.

추천에 걸린 조건(출시 전에 확인합니다):
1. 개인 계정과 개인 카드로 가입·결제가 되는지
2. 그 VM 에서 컴파일 일꾼의 탈출 시험(`docs/DEPLOY.md` 점검표의 `escape.js`)이 통과하는지
   - Ubuntu 를 쓰면 `kernel.apparmor_restrict_unprivileged_userns=0` 이 필요할 수 있습니다.
   - 안 되면 Debian 이미지를 쓰거나 nsjail 로 갑니다.
3. 4GB 에서 일꾼이 버티는지
   - compose 의 일꾼 상한(`mem_limit: 4g`)은 VM 전체 메모리와 같습니다. 그래서 4GB VM 에서는 일꾼 상한을 2g 로 낮추고 `COMPILER_CONCURRENCY=1` 로 둡니다(가정).
   - 한국어 템플릿 컴파일에 필요한 메모리는 재지 않았습니다. 재 보고 모자라면 16GB 묶음으로 올립니다(가정).

**국내 클라우드를 고를 이유가 생기는 경우**:
- 원화 청구·세금계산서가 필요해질 때(사업자등록 뒤)
- 공공기관·학교 고객이 국내 클라우드 보안 인증(CSAP)을 요구할 때(확인 필요)

## 4. DB

### SQLite 를 유지하는 근거

`docs/PRODUCT.md` 의 "DB 와 백업"과 같은 판단입니다.
- **쓰기 양이 작습니다.** 가정으로 1만 명이 하루 20건씩 쓰면 초당 2–3건입니다. 부하 시험은 하지 않았습니다.
- **앱이 이미 1프로세스 전제입니다.** 사용자당 동시 1개(AI·컴파일)와 컴파일 대기열을 메모리로 관리합니다. 그래서 DB 만 바꿔서는 여러 대가 되지 않습니다.
- **운영이 단순합니다.** 데이터가 파일 하나라 백업·복구도 단순합니다. 이미 서버 안에서 하루 스냅숏을 만듭니다.

**Postgres 로 옮기는 조건**(하나라도 해당하면 옮깁니다):
1. 앱 서버를 두 대 이상 띄워야 할 때(메모리 잠금·대기열도 함께 옮겨야 함)
2. 결제 기록 때문에 수 초 단위의 시점 복구가 필요한데, 아래 연속 복제로 부족할 때
3. 쓰기 대기(`busy_timeout = 5000` 에 걸림)가 실제로 관측될 때

`node:sqlite` 는 Node 22 에서 실험 기능입니다. 그래서 Node 판을 고정하고, 올릴 때 시험합니다.

### 백업 방식 비교

| 방식 | 무엇 | 잃는 범위(RPO) | 라이선스 | 장점 | 단점 |
| --- | --- | --- | --- | --- | --- |
| **A. `VACUUM INTO` 스냅숏 + 외부 복사** | 서버가 이미 하루 한 번 스냅숏을 만듦(`server/src/backup.ts`). 백업 일꾼이 restic 으로 암호화해 서버 밖 저장소에 올림 | 최대 24시간 | SQLite 내장. restic 은 BSD 2-Clause, rclone 은 MIT(각 저장소 README, 2026-10-15 확인) | 이미 절반이 구현됨. 스냅숏이 그 자체로 열리는 SQLite 파일이라 복구가 단순함. restic 이 중복을 빼고 암호화함 | 하루 사이의 기록을 잃음. 스냅숏 시각을 바꾸려면 코드 변경 |
| B. Litestream 연속 복제 | 별도 프로세스가 WAL 을 따라가며 S3 호환 저장소로 계속 복제 | 수 초 ~ 수 분(설정) | Apache-2.0(저장소 LICENSE, 2026-10-15 확인). 최신 v0.5.17 | 결제 기록처럼 하루를 잃으면 안 되는 데이터에 맞음 | 아래 주의점. v0.5 에서 저장 형식이 LTX 로 바뀌고 여러 복제 대상 지원이 빠짐(릴리스 노트). 복구 절차가 A 보다 한 단계 많음 |

Litestream 을 붙일 때 확인할 점(문서 저장소의 tips 에서 읽은 것. 요약 도구를 거친 인용이라 원문을 다시 볼 것):
- WAL 모드에서만 동작합니다. 앱은 이미 `journal_mode = WAL` 입니다.
- Litestream 이 읽기 잠금을 잡아 다른 프로세스의 체크포인트를 막습니다. 앱의 `busy_timeout` 은 문서가 권하는 5초와 같습니다.
- DB 파일만 지우고 WAL 을 남기면 안 됩니다. 복구 때 `-wal`·`-shm` 도 함께 다룹니다(`docs/DEPLOY.md` 의 되살리기 절차와 같습니다).
- 앱의 하루 `VACUUM INTO` 와 함께 돌려도 되는지는 시험하지 않았습니다.

`VACUUM INTO` 에 대해: 검색 요약에 따르면 SQLite 문서가 이것을 실행 중인 DB 의 백업 수단으로 설명하고, 만든 파일에 fsync 를 하지 않는다고 적습니다. sqlite.org 를 직접 열지 못해 **확인 필요**입니다. 그래서 백업 일꾼은 restic 으로 올리기 전에 `PRAGMA integrity_check` 를 돌립니다.

**결정(제안)**:
- **베타**: A 를 씁니다. 서버 밖 저장소는 같은 리전의 S3(서울)입니다. 복사 주기는 하루 1회(스냅숏 생성 뒤)이고, restic 보관 정책은 하루 14개·주 8개·월 6개입니다(가정).
- **두 번째 사본(선택)**: 다른 회사의 저장소에 둡니다(예: Cloudflare R2). 호스팅 계정이 정지되는 사고에 대비하는 것입니다.
  - R2 는 Standard $0.015/GB·월이고, 매월 10GB 까지 무료이며, 내려받는 전송료가 없습니다(공식 문서 저장소, 2026-10-15).
  - 저장 위치는 `apac` 같은 힌트만 줄 수 있고 보장되지 않습니다. 한국을 지정할 수도 없습니다. 그래서 이 사본은 국외 이전 항목에 들어갑니다.
- **결제를 켜기 전(M5)**: B 를 더해 RPO 를 줄입니다. A 는 매일 열어 보기 쉬운 사본으로 그대로 둡니다.

### 복구 목표

| 항목 | 베타(결제 없음) | 결제를 켠 뒤(M5) |
| --- | --- | --- |
| 목표 복구 시점(RPO, 잃어도 되는 최대 기간) | 24시간(하루 스냅숏) | 1분 이내(연속 복제) |

### 복구 훈련 절차

- **이미 한 것**: `docs/DEPLOY.md` 의 훈련(2026-10-14)입니다. 개발 환경에서 같은 디스크의 스냅숏으로 되살렸습니다.
- **여기서 더하는 것**: 운영 구성(Docker 볼륨, 서버 밖 복사, 새 VM)까지 포함한 훈련입니다.
- **언제**: 공개 전에 한 번, 결제를 켜기 전에 한 번, 그 뒤 분기마다 한 번 합니다.

1. 운영과 다른 새 VM(또는 같은 VM 의 다른 compose 프로젝트·볼륨)을 준비합니다.
2. **서버 밖 저장소에서** 가장 최근 스냅숏을 받아 복호합니다. 복호 키를 비밀번호 관리자에서 꺼내는 것까지 훈련에 넣습니다.
3. `sqlite3 <파일> "PRAGMA integrity_check"` 가 `ok` 인지 봅니다.
4. 스냅숏을 새 볼륨의 `alldoc.sqlite` 로 넣고, 운영과 같은 이미지 다이제스트로 띄웁니다.
5. `/api/health` 를 확인합니다. 관리자 도구(`admin.js user`, `audit`)로 아는 계정 하나와 마지막 관리 기록이 있는지 봅니다.
6. 다음을 이 문서 아래 "훈련 기록"에 적습니다.
   - 걸린 시간(RTO)
   - 스냅숏 시각과 사고를 가정한 시각의 차(RPO)
   - 막힌 곳

훈련 기록(운영 구성): 아직 없음.

| `BILLING_*`(PG 키·웹훅 비밀) | 결제(M5) | 계획 | PG 관리 화면에서 재발급 → 교체 → 시험 결제·웹훅 확인 | 결제창이 잠깐 실패할 수 있음. 한가한 시간에 |
| `BILLING_ENC_KEY` | 빌링키 AES-256-GCM 암호화(M5, 자동결제 때만) | 계획 | **값만 바꾸면 기존 빌링키를 못 읽습니다.** 암호문에 키 판 번호를 붙이고(`v1:…`) 새 키로 다시 암호화하는 관리자 명령을 M5 에서 함께 만듦 | 그 명령 전까지 교체 금지 |
| 메일 발송 키, 오류 추적 DSN | 메일·오류 추적 | 계획 | 서비스에서 재발급 → 교체 | 작음 |
| 백업 저장소 키, 백업 암호 | 백업 일꾼 | 계획 | 키는 재발급. **백업 암호를 바꾸면 옛 스냅숏은 옛 암호로만 열리므로** 보관 기간 동안 둘 다 보관 | 작음 |

보관 위치(베타):
- **서버**
  - `/etc/alldoc/alldoc.env`(소유자 root, 권한 600)를 운영 compose 의 `env_file` 로 읽습니다.
  - 저장소의 `.env` 는 개발용으로만 씁니다.
  - 일꾼에게는 지금처럼 `COMPILER_SECRET` 하나만 넘깁니다.
- **원본 보관**
  - 운영자의 비밀번호 관리자에 같은 값을 둡니다(어느 것을 쓸지는 사용자가 정함).
  - 백업 암호와 `BILLING_ENC_KEY` 는 **서버가 사라져도 남아야 하므로** 반드시 서버 밖에 둡니다.
- **CI**
  - GitHub Actions 비밀에는 배포용 SSH 키 하나만 둡니다(6장).
  - 앱 비밀값은 CI 에 두지 않습니다.
- **공개 저장소라서**: 비밀값을 커밋하지 않습니다. 공개 저장소에 GitHub 비밀 검사(secret scanning)가 켜져 있는지 확인합니다.
- **늘어난 뒤**: 서버가 여러 대가 되면 클라우드의 비밀 관리 서비스나, SOPS(age)로 암호화해 저장소 밖에 둔 파일로 옮깁니다.

교체 시기:
- **즉시**: 운영자 기기 분실, 유출 의심
- **정기**: 1년에 한 번 `ANTHROPIC_API_KEY`·PG 키를 교체합니다(가정, 사용자가 정함).

## 6. 배포 자동화

### 흐름

```
main 에 push ─► CI(test·no-docx·docker, 바뀐 곳에 따라 latex) 통과
            ─► 이미지 빌드 → GHCR: ghcr.io/<소유자>/alldoc:<커밋>, alldoc-compiler:<커밋>
            ─► (사람이 실행) 배포 작업 → SSH → 서버의 deploy.sh <커밋>
                  1) 두 이미지를 다이제스트로 받음
                  2) 배포 직전 스냅숏을 만들고 서버 밖으로 복사(VACUUM INTO, 이름에 커밋을 붙임)
                  3) docker compose up -d
                  4) /api/health 가 30초 안에 200 이고 version 이 새 커밋인지 확인
                  5) 실패하면 이전 다이제스트로 되돌리고 알림(아래 마이그레이션 주의)
```

- **레지스트리**
  - GHCR 을 씁니다. 지금 CI 는 이미지를 만들어 시험하고 버립니다.
  - 올리는 작업은 CI 가 통과한 `main` 에서만 돌리고, `GITHUB_TOKEN` 의 `packages: write` 권한을 씁니다.
  - 이미지를 공개로 두면 서버가 받을 때 인증이 필요 없습니다. 공개 패키지의 저장·전송 과금 조건은 확인 필요입니다.
- **반영 방식**
  - 베타에는 수동 실행(`workflow_dispatch`) 작업이 SSH 로 서버의 `deploy.sh` 를 부릅니다.
  - 서버 쪽 키는 `authorized_keys` 의 `command=` 로 그 스크립트만 실행하게 묶습니다.
  - Watchtower 같은 자동 갱신은 쓰지 않습니다. 배포 직전 스냅숏을 만들 수 없기 때문입니다.
- **서버에서 빌드하지 않습니다.** 한글 편집기(rhwp-studio)를 빌드할 때 GitHub 에서 받으므로, CI 에서 한 번 빌드한 이미지를 씁니다.
- **건강 확인 보강**(구현 전, 작은 변경)
  - 지금 `/api/health` 는 `{ ok: true }` 만 돌려줍니다.
  - 이미지에 커밋을 넣고(`ARG GIT_SHA`) 응답에 `version` 을 더합니다.
  - DB 에 `SELECT 1` 을 해서 열 수 있는지도 봅니다.
  - 일꾼 연결 상태는 넣지 않습니다. 일꾼이 죽어도 앱의 나머지 기능은 돌기 때문이고, 일꾼은 따로 감시합니다.
- **멈춤 시간**
  - 앱이 한 프로세스라서 교체하는 몇 초 동안 끊깁니다.
  - 베타에서는 받아들이고, 한가한 시간에 배포합니다.
  - 끊김 없는 교체는 앱이 여러 대가 될 때(3장 성장 3) 생각합니다.

### DB 마이그레이션과 배포 순서

지금 동작(확인함, `server/src/db/index.ts`):
- 서버가 켜질 때 `PRAGMA user_version` 보다 뒤의 마이그레이션을 차례로 돌립니다.
- 데이터 파일이 서버가 아는 것보다 새 판이면 **시작을 거부**합니다("데이터 파일이 이 서버보다 새 버전이에요").

그래서 배포는 다음 순서를 지킵니다.
1. **배포 직전 스냅숏**을 만듭니다(위 2단계). 되돌릴 때의 기준점입니다.
2. **마이그레이션은 앞으로만, 옛 코드와 함께 살 수 있게 씁니다.**
   - 열·테이블 추가는 한 번에 해도 됩니다.
   - 열 삭제·이름 바꾸기는 배포 두 번에 나눕니다: 새 열 추가 → 코드가 새 열을 씀 → 다음 배포에서 옛 열 삭제
3. 새 판이 켜지면 마이그레이션이 돌고, 그 뒤 건강 확인을 합니다.

되돌릴 때 주의점:
- **마이그레이션이 없던 배포**: 이미지만 이전 다이제스트로 바꾸면 됩니다.
- **마이그레이션이 있던 배포**: 옛 이미지는 새 판 데이터 파일을 보고 시작을 거부합니다(의도한 동작). 이때 고를 수 있는 길은 둘입니다.
  - (가) 고친 새 판을 다시 내보냅니다.
  - (나) 배포 직전 스냅숏으로 데이터 파일을 되돌리고 옛 이미지를 띄웁니다.
- (나)는 **배포 뒤에 쌓인 기록(가입·사용 횟수·원장·결제)을 잃습니다.** 그래서 결제를 켠 뒤에는 (가)를 기본으로 합니다. (나)는 PG 기록과 대조할 각오가 있을 때만 씁니다.
- 거꾸로 돌리는(down) 마이그레이션은 만들지 않습니다. 시험되지 않은 되돌림 코드가 더 위험하다고 봅니다.
- 일꾼 이미지는 DB 가 없어서 언제든 이전 다이제스트로 바꿀 수 있습니다. 다만 앱과 일꾼 사이의 요청 형식이 바뀌는 배포는 둘을 함께 되돌립니다.

### 로그

- **기존 원칙을 유지합니다.**
  - 문서 글은 로그에 남기지 않습니다. 정상 처리 기록은 종류·글자 수·제안 개수·걸린 시간만 남깁니다(`docs/AI.md`).
  - 원장에도 문서 글이 없습니다.
  - 컴파일 원장은 파일 이름·내용을 남기지 않습니다(`docs/DEPLOY.md` "LaTeX 컴파일").
  - 오류 추적에 보내는 이벤트도 같은 원칙을 따릅니다. 요청 본문, AI 응답 본문, LaTeX 로그를 넣지 않습니다(LaTeX 로그에는 원고 글이 섞입니다).
- **AI 서비스 오류 문장**(최대 500자)은 서버 기록에 남을 수 있습니다(기존 한계, `docs/AI.md`). 그래서 이 문장은 오류 추적에 보내지 않고 오류 코드만 보냅니다.
- **보관 기간**(가정, 처리방침에 그대로 적을 값)
  - 앱·일꾼 기록(표준 출력): Docker `json-file` 기록기에 `max-size=10m`, `max-file=5` 를 걸어 디스크를 지킵니다. 기간은 30일 정도를 목표로 합니다(실제 양을 보고 조정).
  - 프록시 접속 기록(IP 포함): 30일. 남용 조사에 쓰고 지웁니다.
  - 오류 추적: 서비스 보관 기간(아래 표)을 따릅니다.
- **처리방침**: IP 는 개인정보로 다뤄질 수 있습니다. 그래서 처리방침의 수집 항목에 "접속 기록(IP)과 보관 기간"을 넣습니다.

## 8. 메일 발송

필요한 메일(모두 거래 메일이고 광고가 아닙니다):
- 결제 완료·영수증, 환불 완료(M5)
- 이용권 만료 예고(M5)
- 정기결제를 켜면 갱신·가격 변경 고지(`docs/PRODUCT.md` 정기결제 항목)
- 계정 삭제 확인(지금은 화면 확인만 있음. 메일은 선택)
- 운영자 경보

| 후보 | 서울 리전 | 요금(확인 정도) | 비고 |
| --- | --- | --- | --- |
| Amazon SES | 있음(SMTP 엔드포인트 `email-smtp.ap-northeast-2.amazonaws.com`. 검색 요약으로 봄) | 1,000통당 $0.10 이라는 문구와 새 요금제 문구가 함께 보여 **확인 필요** | 호스팅과 같은 계정. 처음엔 시험(sandbox) 상태라 운영 전환 신청이 필요한 것으로 알려짐(확인 필요) |

| NHN Cloud Email | 국내 | 확인 필요 | 국내 사업자 기준 서비스. 개인 가입이 되는지 확인 필요 |

**결정(제안)**: 호스팅을 AWS 로 정하면 **SES 서울 리전**을 씁니다.
- 고른 이유: 같은 계정이고 저장 위치가 국내입니다. 베타의 메일 양(결제 전에는 거의 없음)에서는 요금이 의미 없습니다.
- SES 운영 전환이 사업자 없이 안 되면 Resend 나 Postmark 로 갑니다. 이 둘은 국외 이전 항목에 들어갑니다.
- 메일은 M5(결제) 전까지 꼭 필요하지 않습니다. 그래서 **도메인 인증만 먼저 해 두고 발송 코드는 M5 와 함께** 만듭니다.
- 하루 5,000통 이상 보내는 발신자에게 Gmail 이 요구하는 조건(SPF·DKIM·DMARC, 원클릭 수신 거부, 스팸률 0.3% 미만)은 제3자 자료로만 봤습니다(확인 필요). 거래 메일만 보내는 이 서비스는 그 양에 이르지 않을 것으로 봅니다.

발신 도메인 인증(어느 서비스를 쓰든 필요합니다):
- **메일 전용 하위 도메인**: 예를 들어 `mail.<도메인>` 을 씁니다. 본 도메인의 평판과 분리됩니다.
- **SPF**: 발송 서비스가 알려 주는 `include:` 를 TXT 레코드에 넣습니다.
- **DKIM**: 발송 서비스가 주는 공개키(TXT 또는 CNAME)를 넣습니다.
- **DMARC**:
  - `_dmarc.<도메인>` 에 처음엔 `p=none` 과 보고서 받을 주소로 시작합니다.
  - 보고서에 문제가 없으면 `p=quarantine` 으로 올립니다.
- **답장 주소**: 사용자가 답장할 수 있도록 운영자 문의 주소(`docs/PRODUCT.md` G5 "문의 창구")를 `Reply-To` 로 둡니다.

## 9. 요청 제한과 남용 방지

지금 막는 것과 못 막는 것:
- **막는 것**: 로그인한 사용자 기준의 한도(요금제)와 동시 1개, 서버 전체 컴파일 대기 상한
- **못 막는 것**
  - 로그인 없이 부를 수 있는 경로(`/api/auth/login`, 정적 파일)의 폭주
  - 한 사람이 계정을 많이 만들어 무료 한도를 늘리는 것
  - 큰 파일 업로드(`PUT /api/tex/blobs/:hash`)의 반복

**결정: 두 단계로 나눕니다.**

| 단계 | 맡는 것 | 이유 |
| --- | --- | --- |
| 프록시(Caddy) | IP 기준의 거친 상한. 값은 모두 가정이고 베타 자료로 조정: `/api/auth/*` 분당 10회, `/api/ai/*` 분당 20회, `/api/tex/compile` 분당 10회, `/api/tex/blobs/*` 분당 120회, 나머지 `/api/*` 분당 300회. 업로드 본문 상한도 프록시에 겁니다(요금제의 `projectMaxBytes` 이상) | 앱까지 오기 전에 값싸게 끊습니다. 앱이 IP 를 믿어도 되는지 고민할 필요가 없습니다 |
| 앱 | 사용자 기준: 하루·월 한도, 동시 1개, 전체 하루 비용 차단기, 컴파일 한도·대기열(모두 구현됨) | 사용자와 요금제를 아는 곳은 앱뿐입니다 |

- **앱이 IP 를 써야 할 때**(예: 가입 남용 조사)
  - 프록시가 붙인 `X-Forwarded-For` 의 마지막 값만 믿습니다.
  - 그것도 새 설정 `TRUST_PROXY=1` 을 켰을 때만 읽습니다.
  - 앱 포트가 바깥에 열려 있으면 이 값은 위조할 수 있습니다. 그런데 지금 `docker-compose.yml` 은 `8787:8787` 로 모든 주소에 엽니다. 그래서 **운영 compose 에서는 `127.0.0.1:8787:8787` 로 바꿉니다**.
- **프록시 도구**:
  - Caddy 에는 요청 제한이 기본 지시어로 없습니다(공식 지시어 목록, 2026-10-15). 쓰려면 비공식 플러그인 `mholt/caddy-ratelimit`(Apache-2.0)을 `xcaddy build --with github.com/mholt/caddy-ratelimit` 로 넣은 Caddy 를 따로 빌드해야 합니다. 플러그인 지시어는 순서가 없어서 `order` 나 `route` 로 정해 줘야 합니다.
  - nginx 는 `limit_req`(새는 양동이 방식, 기본 burst 0)가 기본 모듈에 있지만, 인증서 자동 갱신을 따로 붙여야 합니다.
  - **제안**: 인증서 자동 갱신을 잃지 않으려고 **플러그인을 넣은 Caddy 이미지를 CI 에서 만들어** GHCR 에 함께 올립니다. 플러그인이 비공식이라는 점이 위험이고, 문제가 생기면 nginx + certbot 으로 바꿉니다.
  - 앱 단계 IP 제한 라이브러리(`hono-rate-limiter`, MIT)는 README 에 "still in development" 라고 적혀 있습니다. 또 프록시 뒤에서는 소켓 주소가 프록시 주소가 되므로 쓰지 않습니다.
- **IP 를 여럿이 함께 쓰는 곳**: 휴대폰 망·학교·회사는 IP 하나를 여럿이 씁니다. 그래서 상한을 넉넉히 두고, 429 응답에는 한국어 안내 화면을 보여 줍니다.
- **무료 계정 대량 생성**: 1차 방어는 구글 계정 로그인과, 탈퇴 뒤에도 남기는 날짜별 사용 횟수(62일, `docs/PRODUCT.md` 탈퇴 6번)입니다. 그래도 문제가 되면 추가 확인(예: Cloudflare Turnstile)을 그때 넣습니다.

## 11. 출시 점검표

`docs/DEPLOY.md` 의 "공개 전 점검표"를 먼저 끝냅니다. 그 점검표는 라이선스, 이름, 처리방침, 실제 API 키, 지출 한도, 서버 밖 백업, 약관, LaTeX 일꾼 탈출 시험을 다룹니다.
아래는 그 위에 운영 기반으로 더하는 항목입니다.

- [ ] 호스팅 회사·지역을 정하고, 사업자 없이 가입·결제가 되는 것을 확인했다(3장).
- [ ] VM 을 만들었다.
  - SSH 는 키로만 접속하고, 비밀번호 로그인과 root 로그인은 껐다.
  - 방화벽은 80·443 과 22 만 연다(22 는 가능하면 운영자 IP 만).
- [ ] 도메인을 사고 DNS 를 연결했다. Caddy 가 인증서를 받았다.
- [ ] 운영 compose 를 정리했다.
  - 앱 포트를 `127.0.0.1` 에만 열었다.
  - 일꾼은 `compile` 내부망에만 있다.
  - 컨테이너마다 `mem_limit` 과 기록 크기 상한을 걸었다.
- [ ] `/etc/alldoc/alldoc.env` 를 권한 600 으로 두었고, 같은 값을 비밀번호 관리자에 보관했다.
- [ ] 백업을 확인했다.
  - 하루 스냅숏이 암호화되어 서버 밖으로 나간다.
  - 백업 하트비트 감시가 걸려 있다.
  - **운영 구성으로 복구 훈련을 한 번 하고 기록했다**(4장).
- [ ] 가동 감시·디스크·메모리 경보가 운영자에게 실제로 온다(일부러 앱을 멈춰 확인).
- [ ] 오류 추적에 시험 오류를 보내 보고, 요청 본문·문서 글·LaTeX 로그가 들어가지 않는 것을 확인했다.
- [ ] 프록시 요청 제한이 걸린다(같은 IP 로 상한을 넘겨 429 를 확인).
- [ ] 배포를 확인했다.
  - 배포 작업으로 새 판을 올렸다.
  - 일부러 건강 확인에 실패하는 판으로 자동 되돌리기를 확인했다.
- [ ] 메일 발신 도메인의 SPF·DKIM·DMARC 를 넣었다. Gmail 로 받은 메일의 "원본 보기"에서 셋 다 PASS 인 것을 확인했다(메일을 쓰기 시작할 때).
- [ ] 개인정보처리방침에 다음을 적었다(법률 검토 필요).
  - 처리 위탁: 호스팅, 메일, 오류 추적, 백업 저장소
  - 국외 이전: Anthropic, 그리고 해외에 데이터를 두는 서비스
  - 접속 기록 보관 기간, 백업 보관 기간

## 확인하지 못한 것 (이 문서를 쓸 때)

- **서버**: 실제로 VM 을 만들거나 띄워 보지 않았습니다. 가격은 공식 가격 자료를 읽은 값이고, 청구서로 확인한 값이 아닙니다.
- **조사하지 못한 업체**: 네트워크 제한으로 국내 클라우드 3사와 해외 저가 VM 4곳, Render 의 가격·가입 조건을 보지 못했습니다.
- **가입 조건**: 어느 업체든 개인(사업자 없음)이 가입·결제할 수 있는지는 확인하지 못했습니다.
- **격리**: 컴파일 일꾼의 격리(사용자 이름공간·seccomp·AppArmor 해제)가 추천 VM 에서 그대로 되는지, gVisor 와 bubblewrap 을 겹쳐 쓸 수 있는지(`docs/LATEX.md` E3 후속) 확인하지 못했습니다.
- **가정한 값**: 요청 제한 상한, 로그 보관 기간, RPO·RTO, 비용 표의 사용량은 모두 가정입니다.
- **법**: 국외 이전 고지·처리 위탁의 범위는 전문가 확인이 필요합니다.

# 운영자를 믿지 않아도 되는 문서 보관 설계

"운영자를 믿고 서류를 맡기는 대신 블록체인에 보관하자"는 제안을 검토한 결과와, 그 대신 고른 두 기능의 설계입니다.
아직 구현한 것은 없습니다. 재지 않은 값은 비워 두고 실험 뒤에 채웁니다. 제품화 순서는 `docs/PRODUCT.md` 를 봅니다.

정해진 것(2026-10 사용자 결정):
- **문서 본문은 블록체인에 올리지 않습니다.**
- **문서 존재 증명**: 브라우저가 파일 지문(SHA-256)만 계산해 OpenTimestamps 로 비트코인에 기록합니다. 우리 서버 없이도 누구나 검증할 수 있게 합니다.
- **종단간 암호화 서버 저장**: 계획 중인 서버 저장(M6)을 "서버는 암호문만, 열쇠는 사용자 브라우저에만" 방식으로 설계합니다.

"확인 필요"라고 적은 것은 이 문서를 쓸 때 공식 자료로 확인하지 못한 것입니다. 법 항목은 모두 전문가 확인이 필요합니다.
이 문서를 쓴 환경은 네트워크 정책 때문에 `opentimestamps.org`·달력 서버·`solana.com`·`petertodd.org`·OWASP 사이트에 직접 접속하지 못했습니다(프록시가 403 으로 막음). 그래서 GitHub 의 공식 저장소 소스와 검색 결과로 확인했고, 그렇게 확인한 곳을 표시했습니다.

## 가. 왜 본문을 블록체인에 올리지 않는가

| 이유 | 내용 |
| --- | --- |
| 공개되고 영구히 남음 | 공개 체인에 올린 데이터는 지울 수 없고 누구나 복사해 둘 수 있습니다. 암호화해서 올려도, 나중에 그 암호(또는 열쇠)가 깨지면 그때 모두 드러납니다. "지금 안전한 암호문"이 아니라 "영원히 안전한 암호문"이어야 하는데, 그것은 아무도 보장하지 못합니다. |
| 개인정보 파기 의무와 충돌 | 개인정보처리자는 목적을 다한 개인정보를 파기해야 합니다. 2022-07 개인정보 보호법 시행령 개정으로 "블록체인 등에서 영구 삭제가 어려우면, 개인을 알아볼 수 없게 익명 처리해 복원이 불가능하게 한 경우도 파기로 본다"는 근거가 생겼다는 보도가 있습니다([뉴시스](https://www.newsis.com/view/NISX20220711_0001939142), [토큰포스트](https://www.tokenpost.kr/article-83126), [블록미디어](https://www.blockmedia.co.kr/archives/238110)). **조문 번호와 현행 문언은 확인하지 못했습니다**(국가법령정보센터에서 확인 필요). 이 예외가 있어도 공문서·계약서·논문 같은 문서 본문은 사람·기관 이름이 섞여 있어 "복원할 수 없게 익명 처리"하기가 사실상 어렵습니다. |
| 비용 | 솔라나는 계정에 데이터를 두려면 크기에 비례한 예치금(rent-exempt minimum)을 넣어야 합니다. 아래 계산 참고. 지문 32바이트만 올리는 것과 비교하면 수만 배입니다. |
| 사용자 장벽과 규제 | 대상 사용자(공무원·대학원생)에게 지갑 만들기·수수료 충전은 큰 장벽입니다. 토큰을 발행하거나 사용자의 가상자산을 맡아 다루면 「가상자산 이용자 보호 등에 관한 법률」(2024-07-19 시행, [금융위원회](https://www.fsc.go.kr/po010105/82682))·「특정 금융거래정보의 보고 및 이용 등에 관한 법률」의 가상자산사업자 규정이 걸릴 수 있습니다. **어느 경우가 사업자 신고 대상인지 구체 조항은 확인하지 못했습니다.** |

### 솔라나 예치금 계산

- 지금까지 알려진 식은 `(데이터 바이트 + 128) × 3,480 lamports/바이트·년 × 2년 = (바이트 + 128) × 6,960 lamports` 입니다([QuickNode](https://www.quicknode.com/guides/solana-development/getting-started/understanding-rent-on-solana), [RareSkills](https://rareskills.io/post/solana-account-rent)). 1 SOL 은 10⁹ lamports 입니다.
  - 1MiB(1,048,576바이트): (1,048,576 + 128) × 6,960 = 7,298,979,840 lamports ≈ **7.30 SOL**
  - 1,000,000바이트: ≈ 6.96 SOL
- **이 값은 바뀌는 중입니다.** 솔라나 SDK 소스(`anza-xyz/solana-sdk` 의 `rent/src/lib.rs`, 2026-10 확인)에는 면제 기준을 2년에서 1.0 으로 바꾸는 SIMD-0194 경로가 들어 있고, 128바이트 덧붙임(`ACCOUNT_STORAGE_OVERHEAD`)은 그대로입니다. 2026년에 바이트당 단가를 단계적으로 내리고 있다는 문서가 있지만 단계 값이 서로 다릅니다(Raydium 문서는 6,333, Chainstack 문서는 5,080 lamports/바이트). 공식 발표로는 확인하지 못했습니다.
  - 내려간 값으로 계산해도 1MiB 에 약 5.3–6.6 SOL 로, "본문을 올리면 비싸다"는 결론은 같습니다.
  - 실제로 쓸 일이 생기면 상수 대신 `getMinimumBalanceForRentExemption` RPC 로 그때 값을 읽습니다.

### 그래서 대신 하는 것

블록체인이 잘하는 일은 "누구도 고칠 수 없는 시각 기록"입니다. 그래서 문서 대신 **지문(해시)만** 기록해 "그 시점에 이 내용 그대로였다"를 증명하고(나), 보관은 **운영자가 내용을 볼 수 없는 방식**으로 서버에 둡니다(다).

## 나. 문서 존재 증명

### 무엇을 증명하나

- 증명하는 것: "이 파일(바이트 하나하나 같은 것)이 **늦어도 이 시각에는 존재했다**."
- 증명하지 않는 것:
  - 누가 만들었는지(작성자). 지문에는 이름이 없습니다.
  - 그 시각 **이전**에 없었다는 것
  - 내용이 참이라는 것, 법적 효력
- 한 바이트라도 다르면 지문이 달라지므로, 증명은 **그때의 파일 그대로**와 함께 보관해야 합니다.

### OpenTimestamps 동작 (확인한 것)

- 무료, 가입 없음. 달력 서버(calendar)가 받은 지문들을 Merkle 트리로 묶어 비트코인 거래 하나에 기록합니다. 처음에는 "달력 서버가 받았다"는 미완성 영수증(pending)을 즉시 돌려주고, 비트코인에 확정된 뒤 영수증을 완전한 증명으로 업그레이드합니다([발표 글](https://petertodd.org/2016/opentimestamps-announcement), 이전 세션에서 확인. 이번 환경에서는 열지 못함).
- 공식 클라이언트(`opentimestamps/opentimestamps-client`, 2026-10 소스 확인):
  - README: "It takes a few hours for the timestamp to get confirmed by the Bitcoin blockchain." 확정 전에는 `ots verify` 가 실패하고, 완전한 로컬 검증에는 비트코인 코어 노드가 필요합니다.
  - `otsclient/cmds.py` 의 `stamp`: 파일마다 **16바이트 무작위 값(nonce)을 지문 뒤에 붙여 다시 SHA-256** 한 값을 보냅니다. 주석의 이유: 파일과 영수증이 나중에 따로 돌아다닐 수 있어서, nonce 가 없으면 함께 묶인 다른 파일의 지문이 새어 나간다.
  - 기본 달력 서버(소스 기준 4곳): `https://a.pool.opentimestamps.org`, `https://b.pool.opentimestamps.org`, `https://a.pool.eternitywall.com`, `https://ots.btc.catallaxy.com`. README 에는 앞의 3곳만 적혀 있어 소스와 다릅니다. 운영 전에 opentimestamps.org 에서 다시 확인합니다.
  - 여러 달력 서버에 동시에 보내고 그중 정해진 수(m-of-n) 이상 응답하면 성공으로 봅니다.

### 흐름

```
브라우저                                   우리 서버(중계)                 달력 서버들
1. 파일 바이트 고정(스냅숏)
2. h = SHA-256(파일)          (crypto.subtle.digest)
3. n = 무작위 16바이트         (crypto.getRandomValues)
4. d = SHA-256(h ‖ n)
5. POST /api/stamp {d}  ───────────────▶  d 만 받음(32바이트) ──────────▶ POST /digest
                                           pending 영수증들 ◀──────────── 즉시 응답
6. .ots 조립(h, append n, sha256, pending) ◀──
7. IndexedDB 에 스냅숏 + .ots 저장
  … 몇 시간 뒤(앱을 다시 열 때) …
8. POST /api/stamp/upgrade {calendar, d} ─▶ GET /timestamp/<d> ─────────▶
9. 완성된 경로로 .ots 갱신   ◀───────────── Bitcoin 기록 경로 ◀────────
```

- `.ots` 는 공식 형식(DetachedTimestampFile)을 그대로 씁니다. 그래야 공식 도구로 우리 없이 검증됩니다.
- 영수증 안에는 `h`(파일 지문)와 `n` 이 들어 있습니다. 서버에는 `d` 만 갑니다.

### 제출: 브라우저가 직접 vs 우리 서버가 대신

| | 브라우저가 달력 서버에 직접 | 우리 서버가 중계 |
| --- | --- | --- |
| CSP | 사이트 전체 `connect-src 'self' blob: data:`(`server/src/app.ts` 의 `CONTENT_SECURITY_POLICY`)에 달력 서버 4곳을 더해야 함. 달력 목록이 바뀌면 배포가 필요 | 지금 CSP 그대로 |
| CORS | 달력 서버가 다른 출처의 요청을 허용해야 함. `javascript-opentimestamps` README 는 브라우저에서도 쓸 수 있다고 하지만, **지금 달력 서버들이 CORS 헤더를 주는지는 확인하지 못했습니다** | 상관없음 |
| 사용자 IP | 제3자(달력 운영자)에게 사용자 IP 와 우리 사이트 출처(`Origin`)가 보임 | 달력 서버는 우리 서버 IP 만 봄. 우리 서버는 원래 사용자 IP 를 봄 |
| 우리 서버가 아는 것 | 없음 | `d`(무작위처럼 보이는 32바이트)와 요청 시각, 로그인했다면 사용자. 파일 내용·파일 지문 `h` 는 모름(nonce 때문) |
| 가용성 | 우리 서버가 죽어도 제출 가능 | 우리 서버가 죽으면 새 제출 불가. **이미 받은 영수증의 검증에는 영향 없음** |
| 남용 막기 | 못 함(사용자가 직접 보냄) | IP·사용자별 요청 제한, 32바이트 외 거절 |
| 사내망 설치 | 사용자 PC 가 밖으로 나갈 수 있어야 함 | 서버만 나갈 수 있으면 됨. 막힌 곳은 `STAMP_MODE=off` |

**권장: 우리 서버 중계.** CSP 를 넓히지 않고, 확인하지 못한 CORS 에 기대지 않으며, 사용자 IP 를 제3자에게 넘기지 않습니다. 서버가 아는 것은 nonce 를 거친 지문뿐이라 "운영자를 믿지 않아도 된다"는 목표와도 맞습니다. 검증은 처음부터 우리 서버 없이 됩니다.
- 서버 경로: `server/src/stamp/{routes,calendar}.ts`(새로)
  - `POST /api/stamp`: 본문은 정확히 32바이트(16진수 64자)만 받습니다. 여러 달력에 동시에 보내고, 2곳 이상 응답하면 성공입니다(수는 실험 뒤 확정).
  - `POST /api/stamp/upgrade`: 달력 주소는 **허용 목록에 있는 것만** 받습니다(임의 주소로 요청을 보내게 하는 SSRF 막기).
- 로그인 없이도 쓸 수 있게 하고, IP 기준 요청 제한을 겁니다. 서버 기록에는 `d` 를 남기지 않습니다(개수·걸린 시간·성공한 달력 수만).
- 설정: `STAMP_MODE=relay|off`(기본 `relay`), `STAMP_CALENDARS`(목록), `STAMP_PROVIDER=mock`(종단 시험용, 정해진 영수증을 돌려줌). AI 연결부처럼 `AppDeps` 로 주입합니다.
- 나중에 요청이 많아지면 서버가 1초 단위로 `d` 들을 Merkle 트리로 묶어 루트 하나만 보내는 집계를 할 수 있습니다. 첫 버전에는 넣지 않습니다.

### 증명 보관

- `web/src/lib/docs.ts` 의 IndexedDB 에 `proofs` 저장소를 추가합니다(DB 버전을 올림).
  - `docs/LATEX.md` 도 같은 DB 를 버전 2 로 올리는 계획(`texFiles`)이라, 먼저 들어가는 쪽이 2, 나중 쪽이 3 이 됩니다. `upgrade` 는 옛 버전별로 나눠 씁니다.
  - 키 `id`, 값 `{id, docId, createdAt, fileName, size, sha256, ots: Uint8Array, status: 'pending' | 'complete', bitcoin?: {height, time}, blob}`, 색인 `by-doc`
  - `blob` 은 **증명한 바로 그 바이트**입니다. 내려받기(`web/src/components/DownloadMenu.tsx`)는 누를 때마다 편집기에서 다시 내보내므로(`opt.run()`), 같은 문서라도 바이트가 매번 같은지 알 수 없습니다(실험 X3). 그래서 스냅숏을 함께 둡니다.
- 증명할 수 있는 것: 올린 원본(`original` 블롭, 바이트가 그대로라 계약서 사본 증명에 알맞음), 지금 고친 내용(저장을 마친 뒤 `working` 블롭).
- 내려받기: "증명과 함께 내려받기"는 `이름.hwp` 와 `이름.hwp.ots` 두 파일을 받습니다. 두 파일을 묶은 zip 도 고를 수 있게 합니다.
- `removeDoc` 은 증명을 함께 지울지 묻습니다. 증명은 문서보다 오래 가치가 있을 수 있으므로 기본은 "남기기"입니다.
- 업그레이드는 앱이 열려 있을 때만 합니다(백그라운드 작업 없음). 증명 목록을 열 때 `pending` 이고 만든 지 1시간 넘은 것을 업그레이드합니다(간격은 실험 뒤 조정).

### 검증

**우리 서버 없이**(공개 도구):
- 공식 파이썬 클라이언트: `pip install opentimestamps-client` 후 `ots verify 이름.hwp.ots`(같은 폴더에 `이름.hwp`). 완전한 검증에는 자기 비트코인 코어 노드가 필요하다고 README 에 적혀 있습니다.
- `ots info 이름.hwp.ots` 로 영수증 안의 경로와 기록 블록을 볼 수 있습니다.
- opentimestamps.org 웹 페이지에서 파일과 영수증을 올려 검증할 수 있다고 알려져 있습니다(이번 환경에서 열지 못해 확인 필요).
- 앱 안내 문서에 이 명령을 그대로 적어, AllDoc 이 사라져도 검증할 수 있게 합니다.

**앱 안의 검증 화면**(`/verify`, 로그인 없이):
1. 파일과 `.ots` 를 올립니다. 브라우저 안에서만 계산하고 파일은 어디로도 보내지 않습니다.
2. 파일의 SHA-256 이 영수증 첫 지문과 같은지 봅니다. 다르면 "이 영수증은 이 파일의 것이 아니거나, 파일이 바뀌었어요".
3. 영수증의 연산을 따라 계산해 비트코인 블록 높이와 기대하는 Merkle 루트를 얻습니다.
4. 그 블록의 실제 머리(header)와 비교해야 완전한 검증입니다. 브라우저는 블록 머리를 스스로 가질 수 없으므로 출처를 밝힙니다.

5. 결과 문구: "이 파일은 늦어도 **2026-10-12 14:03(한국 시각) 무렵**에는 지금 내용 그대로 존재했습니다(비트코인 블록 N)." 블록 시각은 몇 시간 오차가 있을 수 있어 "무렵"이라고 씁니다.

## 다. 종단간 암호화 서버 저장 (`docs/PRODUCT.md` M6 를 대체하는 안)

### 목표와 한계

- 목표: 서버(와 서버를 가진 운영자, 서버를 턴 사람)는 **암호문만** 봅니다. 열쇠는 사용자 브라우저에만 있고 서버로 가지 않습니다.
- 서버 저장은 지금처럼 **문서별로 고르는 기능**이고, 브라우저 저장이 기본입니다.
- **웹 앱 종단간 암호화의 근본 한계**: 암호화하는 자바스크립트를 운영자가 내려보냅니다. 운영자가 악의를 품거나 서버가 털려서 바뀐 스크립트를 내려보내면 암호문구를 빼낼 수 있습니다. 이 설계는 "지금 서버에 쌓인 데이터만으로는 못 읽는다"를 보장하지, "운영자가 앞으로도 절대 못 읽는다"를 보장하지 않습니다.
  - 줄이는 방법: AGPL 로 소스 공개, 빌드 결과물의 해시를 저장소에 공개해 누구나 대조할 수 있게 하기(재현 가능한 빌드 확인 필요). 화면과 문서에 이 한계를 그대로 적습니다.

### 열쇠

**계층**:
```
암호문구 ──PBKDF2──▶ KEK_p ─┐
                             ├─ 감쌈 ─▶ MK(계정 열쇠, 무작위 256비트) ─ 감쌈 ─▶ DEK(문서마다 무작위 256비트) ─▶ 파일 암호화
복구 코드 ──HKDF───▶ KEK_r ─┘
```
- **MK(계정 열쇠)**: 처음 켤 때 브라우저가 `crypto.getRandomValues` 로 만듭니다. 서버에는 KEK_p 로 감싼 것과 KEK_r 로 감싼 것 두 벌만 갑니다.
- **DEK(문서 열쇠)**: 문서마다 따로 만들고 MK 로 감싸 문서 정보와 함께 서버에 둡니다.
  - 암호문구를 바꿔도 MK 만 다시 감싸면 되고, 문서를 다시 암호화하지 않습니다.
  - 문서 하나를 지우면 그 DEK 를 지워 그 문서만 못 읽게 할 수 있습니다.
- 감싸기는 WebCrypto `wrapKey`(AES-KW) 또는 AES-GCM 으로 합니다.
- 이 기기에 MK 를 기억할 때는 `extractable: false` 인 `CryptoKey` 를 IndexedDB 에 둡니다(스크립트가 열쇠 바이트를 꺼낼 수 없음). "이 기기 기억하지 않기"를 고르면 탭을 닫을 때 버립니다.

**암호문구에서 열쇠 만들기(KDF)**:
- 서버가 감싼 MK 와 소금값(salt)을 갖고 있으므로, 서버 자료를 가진 사람은 암호문구를 오프라인으로 마구 대입해 볼 수 있습니다. 그래서 느린 KDF 와 충분히 긴 암호문구가 모두 필요합니다.
- 브라우저 WebCrypto 가 기본으로 주는 암호문구 KDF 는 **PBKDF2** 뿐입니다(HKDF 는 이미 강한 열쇠용).
  - Argon2 는 WICG "Modern Algorithms in WebCrypto" 초안에 들어 있고 Node.js 는 구현했지만, 크롬이 브라우저에 넣었다는 자료는 찾지 못했습니다(2026-10 검색. 크롬의 2026-06 실험 공지는 양자 내성 알고리즘과 ChaCha20-Poly1305 만 다룸). **확인 필요**.
- **권장 1차안: PBKDF2-HMAC-SHA256, 600,000회**, 소금값 16바이트 무작위.
  - 근거: OWASP Password Storage Cheat Sheet(저장소 원문 2026-10 확인)의 PBKDF2-HMAC-SHA256 권장값 600,000회.
  - 휴대폰에서 걸리는 시간은 재지 않았습니다(실험 Y1). 잠금 해제할 때 한 번만 하므로 1–2초까지는 받아들일 수 있다고 봅니다.
- 나중 안: Argon2id. OWASP 최소 설정은 `m=19456(19MiB), t=2, p=1`(같은 문서). WASM 라이브러리 후보는 `hash-wasm`(MIT, 4.12.0)·순수 JS `@noble/hashes`(MIT, 2.4.0, 느림). 브라우저가 Argon2 를 기본 제공하면 옮깁니다.
- 감싼 MK 옆에 `{kdf: 'pbkdf2-sha256', iterations, salt, v: 1}` 를 함께 저장해, 나중에 매개변수·방식을 올릴 때 다음 잠금 해제에서 다시 감쌉니다.
- 암호문구 규칙: 최소 길이(예: 12자)와 흔한 암호 거르기. 서버는 암호문구를 받지 않으므로 이 검사는 브라우저에서만 합니다.

**복구 코드**:
- 켤 때 무작위 128비트를 만들어 읽기 쉬운 글자(예: 4자씩 8묶음)로 보여 주고, **다시 입력하게 해서** 적어 둔 것을 확인합니다. 내려받기(txt)·인쇄도 제공합니다.
- 엔트로피가 충분하므로 느린 KDF 대신 HKDF-SHA256 으로 KEK_r 를 만듭니다.
- 복구 코드로 들어오면 새 암호문구를 정하게 하고, 새 복구 코드를 만들지 고르게 합니다.

**잃었을 때 안내 문구**(켤 때 확인란과 함께, 초안):
> 암호화 저장을 켜면 문서는 이 기기에서 잠근 뒤 서버로 올라갑니다. **운영자도 문서를 열 수 없습니다.**
> 암호문구와 복구 코드를 **모두 잃으면 서버에 있는 문서는 누구도 되살릴 수 없습니다.** 운영자에게 문의해도 도와드릴 수 없습니다.

### 암호화

- WebCrypto **AES-256-GCM**. 암호화할 때마다 **새 무작위 IV 12바이트**를 만듭니다(같은 열쇠로 IV 를 다시 쓰면 GCM 이 깨지므로, 저장할 때마다 새로 만듦). 무작위 IV 를 쓸 때 한 열쇠로 암호화하는 횟수는 2³² 회를 넘기지 말라는 NIST SP 800-38D 의 제한이 있는데(널리 알려진 값이며 이번에 원문을 다시 열어 보지는 않음), 문서마다 DEK 를 따로 두므로 닿지 않습니다.
- 추가 인증 데이터(AAD)에 `{v, userId, docId, revision, 파일 경로}` 를 넣습니다. 서버가 다른 문서·다른 판의 암호문을 바꿔치기하면 복호화가 실패합니다.
- 파일 하나 = 암호문 하나. 첫 버전은 파일 전체를 한 번에 암호화합니다(지금 여는 파일 상한 `MAX_FILE_BYTES` 범위). 아주 큰 파일을 위한 조각 암호화는 나중입니다.
- **메타데이터도 암호화합니다**: 문서 이름, 종류, 원래 크기, 고친 여부, LaTeX 파일 목록·경로, 증명(.ots) 목록. 문서마다 "암호화된 목록(manifest)" 하나에 담습니다.
- 크기는 숨길 수 없으므로, 암호문 크기를 일정 단위(예: 64KiB 배수)로 채워(padding) 대략만 드러나게 할지 고릅니다. 저장 용량이 늘어나는 비용이 있어 **사용자 결정**으로 둡니다.

| 문서 수 | 앎 | |
| 문서·파일별 암호문 크기 | 앎(채우기를 하면 대략만) | |

### 충돌 지점과 대처

**내용 해시 중복 제거**(`docs/PRODUCT.md` M6 의 "파일은 내용 해시 이름으로 저장", `user_blobs`, `docs/LATEX.md` 의 `POST /api/tex/blobs/check`):
- 무작위 IV 때문에 같은 평문도 암호문이 매번 다르므로, 암호문 해시로는 중복이 제거되지 않습니다. 평문 해시를 서버에 보내면 "이 사용자가 이 공개 파일(예: 유명한 양식)을 갖고 있다"가 드러납니다.
- 대처:
  1. 서버 저장소의 이름은 **암호문의 SHA-256** 으로 합니다(서버가 받은 바이트를 확인하는 용도, 중복 제거 아님).
  2. 중복 제거는 **브라우저가** 합니다. 암호화된 목록에 파일마다 `HMAC(MK 에서 유도한 열쇠, 평문)` 을 적어 두고, 바뀌지 않은 파일은 다시 올리지 않습니다. LaTeX 처럼 파일이 많은 프로젝트에서 이것이 중요합니다.
  3. 서버에 HMAC 값을 보내 "있나요?"를 묻는 방식은 쓰지 않습니다(같은 사용자 안의 같은 내용 여부만 새지만, 2번으로 충분하므로 필요 없음).
- 결과: 사용자 사이 중복 제거는 하지 않습니다. 저장 용량 원가가 늘 수 있으며 요금제 `storageBytes` 로 묶습니다.

**LaTeX 서버 컴파일과 AI 기능**은 평문이 필요합니다.
- 컴파일: 프로젝트 파일 평문이 우리 컴파일 서버로 갑니다.
  - 암호화 프로젝트에서는 "컴파일 뒤 서버에 남기지 않기"(`docs/LATEX.md`)를 **강제로 켭니다**.
  - 컴파일 결과 캐시(`sha256(목록 + 엔진 + TeX Live 판)`)를 쓰지 않습니다. 캐시 키가 평문 해시이기 때문입니다.
  - 받은 PDF 는 브라우저가 암호화해 저장합니다.
- AI: 문단 글이 우리 서버를 거쳐 AI 서비스(기본 Anthropic, 미국)로 갑니다(`docs/AI.md`). 서버는 지금처럼 문서 글을 기록하지 않습니다.
- 알리는 흐름:
  1. 암호화 문서에서 컴파일·AI 를 처음 쓰려 하면 따로 확인 창을 띄웁니다.
     > 이 문서는 암호화되어 저장돼 있지만, **컴파일(또는 AI)을 쓰려면 문서 내용을 잠그지 않은 채로 보내야 합니다.**
     > 보내는 곳: AllDoc 컴파일 서버(끝나면 지움) / AllDoc 서버를 거쳐 AI 서비스(Anthropic, 미국)
     > [이번만 보내기] [이 문서는 계속 허용] [보내지 않기]
  2. 허용하면 도구줄에 "암호화 문서 · 컴파일·AI 때 내용을 보냄" 표시를 둡니다. 설정에서 문서별 허용을 거둘 수 있습니다.
  3. 문서마다 "평문을 서버로 보내지 않기" 잠금을 고를 수 있습니다. 켜면 그 문서에서 AI·컴파일 단추가 꺼지고 이유를 보여 줍니다.
  4. 기존 AI 동의(`web/src/components/ConsentDialog.tsx`)는 그대로 두고, 위 확인은 그 위에 문서별로 더합니다.
- 브라우저 안에서 하는 일(서식 점검의 "문서 안 일관성"·"기준 문서", 존재 증명의 지문 계산)은 평문을 보내지 않으므로 이 확인이 필요 없습니다.

### 여러 기기, 동기화 충돌

- 새 기기: 구글 로그인 → 서버에서 감싼 MK·KDF 매개변수를 받음 → 암호문구 입력 → MK 를 풀어 이 기기에 기억(고르면).
- 충돌: 지금 M6 설계를 그대로 씁니다. 저장할 때 기준 판 번호를 보내고, 다르면 409 를 받습니다.
  - 서버는 내용을 볼 수 없으므로 **합치는 일은 모두 브라우저가** 합니다.
  - 한글·Word 같은 이진 파일은 합치지 않고 "충돌본" 사본을 만듭니다.
  - LaTeX 는 두 판의 암호화된 목록을 브라우저가 풀어 파일 단위로 비교합니다.
- 기기 분실: "모든 기기에서 로그아웃"(`session_version`, `docs/PRODUCT.md`)만으로는 분실한 기기에 기억된 MK 를 지우지 못합니다. 걱정되면 암호문구를 바꾸고 MK 자체를 바꾸는 "열쇠 교체"(모든 DEK 를 새 MK 로 다시 감쌈)를 제공합니다. 이미 그 기기에 내려받아 둔 문서는 막을 수 없다고 안내합니다.

### 탈퇴·삭제

- 문서 삭제: 암호문, 감싼 DEK, 그 문서의 목록을 지웁니다.
- 탈퇴(`docs/PRODUCT.md` "탈퇴와 보관" 5단계): 모든 암호문과 감싼 MK 두 벌, 감싼 DEK 를 지웁니다.
- 백업: 하루 1회 스냅숏을 14개 보관하는 계획(`docs/PRODUCT.md`)이라, 지운 뒤에도 최대 14일 동안 백업에 **암호문과 감싼 열쇠**가 남습니다. 암호문구 없이는 읽을 수 없지만, 그 기간 동안은 약한 암호문구를 대입하는 공격 대상이 남는다는 뜻입니다. 개인정보처리방침에 그대로 적습니다.

### 백업과의 관계

- 서버 백업에는 암호문만 들어가므로 백업이 새어도 내용은 드러나지 않습니다(위 대입 공격 예외).
- 서버 백업으로 되살릴 수 있는 것은 "암호문"뿐입니다. 사용자가 열쇠를 잃으면 백업이 있어도 소용없습니다.
- 그래서 "전체 내보내기(zip)"는 브라우저가 풀어서 **평문으로** 만들어 줍니다. 열쇠 분실에 대비한 사용자 쪽 백업 수단으로 안내합니다.
- 복구 훈련(`docs/PRODUCT.md` G5)은 "백업에서 되살린 서버 + 시험 계정의 암호문구로 문서가 열린다"까지 확인합니다.

### 서버 쪽 구조 (초안)

```sql
CREATE TABLE key_bundles (user_id TEXT PRIMARY KEY, v INTEGER NOT NULL,
  wrapped_mk_pass BLOB NOT NULL, kdf TEXT NOT NULL /* JSON: 방식·반복 수·소금값 */,
  wrapped_mk_recovery BLOB NOT NULL, recovery_salt BLOB NOT NULL, updated_at INTEGER NOT NULL);
CREATE TABLE enc_documents (id TEXT PRIMARY KEY, user_id TEXT NOT NULL, wrapped_dek BLOB NOT NULL,
  head_revision INTEGER NOT NULL, created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL, deleted_at INTEGER);
CREATE TABLE enc_revisions (doc_id TEXT NOT NULL, revision INTEGER NOT NULL, manifest_blob TEXT NOT NULL /* 암호문 해시 */,
  bytes INTEGER NOT NULL, created_at INTEGER NOT NULL, PRIMARY KEY (doc_id, revision));
```
- 암호문 파일은 `DATA_DIR/blobs/<암호문 sha256>`(나중에 S3 호환)에 둡니다. 서버는 받은 바이트의 해시만 확인합니다.
- 감싼 열쇠를 바꾸는 요청은 로그인한 본인만, CSRF 막이(`sameOriginOnly`)를 거칩니다. 서버는 감싼 열쇠가 맞는지 확인할 수 없으므로, 브라우저가 올리기 전에 한 번 풀어 보고 올립니다.

### 실험 (구현 전에)

| 실험 | 재는 것 | 결과 |
| --- | --- | --- |
| Y1 KDF 시간 | PBKDF2-SHA256 600,000회를 데스크톱 크롬·사파리와 휴대폰(가능하면)에서 | 아직 재지 않음(휴대폰은 실기기가 없어 "확인 못 함"이 될 수 있음) |
| Y2 암호화 시간 | 지금 여는 파일 상한 크기의 AES-GCM 암호화·복호화 시간 | 아직 재지 않음 |
| Y3 IndexedDB 의 `CryptoKey` | `extractable: false` 열쇠를 IndexedDB 에 넣고 다시 읽기(크롬·사파리·파이어폭스) | 아직 확인하지 않음 |

### 시험 계획

- 단위 시험(`web/src/lib/vault/*.test.ts`, Node 의 WebCrypto 사용):
  - 열쇠 계층: 암호문구로 MK 풀기, 복구 코드로 MK 풀기, 틀린 암호문구는 실패, 암호문구 바꾼 뒤 옛 문구 실패·새 문구 성공·문서는 다시 암호화하지 않음
  - 같은 평문을 두 번 암호화하면 IV 와 암호문이 다름(IV 를 고정하면 이 시험이 실패하는지 확인)
  - AAD: 다른 문서·판의 암호문을 끼우면 복호화 실패
  - 암호화된 목록에 이름이 평문으로 들어가지 않음(암호문 바이트에 문서 이름 바이트열이 없음)
  - KDF 매개변수 올리기: 옛 매개변수로 감싼 MK 를 풀면 새 매개변수로 다시 감쌈
- 서버 시험: 서버로 가는 모든 요청 본문에 평문 문서 이름·내용이 없음(가짜 저장소로 기록해 검사), 409 충돌, 본인만 접근, 탈퇴 시 모두 지움
- 종단 시험(`e2e/vault.spec.ts`): 두 브라우저 문맥으로 켜기 → 복구 코드 확인 → 저장 → 다른 문맥에서 암호문구로 열기 → 같은 문서를 양쪽에서 고쳐 충돌본 생성 → 복구 코드로 들어와 새 암호문구 정하기. 암호화 문서에서 AI 를 누르면 확인 창이 뜨고 "보내지 않기"면 요청이 가지 않음
- 화면 문구는 화면 캡처로 눈으로 확인합니다.
